# TTS·렌더 진단 관리자 화면 - 현황조사 및 구현계획

작성일: 2026-07-29

## 1. 착수 전 현황

- `/admin/diagnostics`(TTS·렌더 진단) URL은 이번 회차 이전에는 존재하지 않았다.
- 관련 실데이터는 이미 DB에 쌓여 있었다: `content_tts_master`, `content_tts_sentences`,
  `content_mp4`(단계9에서 `render_method`·`fallback_reason` 컬럼 추가됨),
  `content_render_diagnostics`(단계9, 브라우저 WebGPU/WebCodecs 탐지 결과).
- FFmpeg·FFprobe는 `app/config.py`의 `FFMPEG_PATH`/`FFPROBE_PATH`로 프로젝트 전용
  경로(`runtime/ffmpeg/bin`)가 이미 정의돼 있었다.
- **TTS 생성 소요시간(latency)을 저장하는 컬럼은 어느 테이블에도 없다.** 확인 방법:
  `content_tts_master`/`content_tts_sentences` 스키마 전체 조회, `app/tts/service.py`의
  `upsert_tts_master` 호출부 확인(성공/실패 시 1회만 호출, pending 단계를 먼저 기록하지
  않아 `created_at==updated_at`이 되므로 master 레벨 delta는 사용 불가).

## 2. 설계 결정 (자동 선택, 최소 수정 우선)

1. **평균 생성시간**: 새 컬럼이나 계측 코드를 추가하는 대신, 이미 존재하는
   `content_tts_sentences.created_at`/`updated_at`의 실제 흐름을 활용했다.
   `replace_tts_sentences()`가 배치 시작 시각으로 전체 문장의 `created_at=updated_at`을
   세팅하고, `upsert_tts_sentence_result()`가 각 문장 합성이 끝난 실제 시각으로
   `updated_at`만 갱신하는 구조이므로, SQL 윈도우 함수(`LAG`)로 문장 간 실제 완료
   시각차를 구해 평균을 냈다. 이는 **추정값**이며 화면에 "추정"이라고 명시한다(사실이
   아닌 것을 사실처럼 보여주지 않기 위함 - 00_READ_FIRST.md 13장 업무일지 원칙을 화면
   문구에도 적용).
2. **FFmpeg·FFprobe 상태**: 단순 파일 존재 여부만 확인하면 "실제 검사"라 보기 어렵다고
   판단해, 페이지를 열 때마다 `subprocess.run([exe, "-version"], timeout=5)`를 실제
   실행해 종료코드와 첫 줄 출력을 보여준다. 관리자가 "다시 검사" 버튼(페이지 새로고침)을
   누르면 그때마다 다시 실제로 실행된다.
3. **Range 응답 검사**: 서버 쪽에서 자기 자신에게 루프백 HTTP 요청을 보내는 대신,
   관리자 브라우저가 실제로 실서비스 라우트(`/content/job/{uid}/mp4/video`, 기존
   단계8·9에서 이미 실측 검증된 Range 스트리밍 라우트)에 `Range: bytes=0-1023` 헤더로
   `fetch()`를 보내고 `206 Partial Content` 여부를 그대로 보여주는 방식을 선택했다.
   최근 완성된 MP4가 있는 프로젝트가 있을 때만 버튼을 활성화한다(없으면 비활성화 +
   이유 표시, 죽은 버튼으로 남기지 않기 위함).
4. **최근 TTS 실패 / 재시도**: 새 재시도 엔진을 만들지 않고 기존 `/content/job/{uid}/tts`
   화면(단계7에서 이미 검증된 문장별 재생성 버튼)으로 안내하는 링크만 제공한다(작업지시
   21장 "완료 산출물을 불필요하게 다시 만들지 않고 실패 단계부터 이어야 한다" 원칙을
   신규 코드 추가 없이 재사용으로 만족).

## 3. 접근 제어

- 페이지: `_require_admin_or_none()` 재사용, 비관리자는 `/dashboard`로 303 리다이렉트.
- Range 검사 버튼이 호출하는 `/content/job/{uid}/mp4/video`는 기존
  `_get_owned_project_or_none()`으로 본인 소유이거나 관리자만 통과(단계5부터 이미 존재).
- 신규 POST 라우트는 만들지 않았으므로(모두 GET 재사용 + 클라이언트 fetch) 별도
  POST 접근제어 지점은 없다.

## 4. E2E 검증 방법

8033 임시 테스트 서버에서 관리자 계정으로 로그인 후 `/admin/diagnostics` 접속,
콘솔·네트워크 오류 확인, Range 검사 버튼 클릭 시 실제 206 응답과 토스트 표시 확인,
일반 사용자 계정으로 GET 접근 시 리다이렉트 확인.
