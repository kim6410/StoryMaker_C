## 2. 단계 6A의 목표

이번 단계는 화면 구조나 DB 틀만 만들고 멈추는 단계가 아닙니다.

실제 Gemini API 호출까지 진행합니다.

다만 한 번에 SNS 8채널 전체 기능까지 확장하지 않고, 아래 범위만 안전하게 완주합니다.

1. 프롬프트 생성기
2. Gemini Adapter
3. 실제 Gemini API 호출
4. JSON 응답 파싱
5. 스키마 검증
6. 오류 상태 분리
7. 중복 호출 방지
8. 호출 이력 최소 저장

이번 단계가 끝난 뒤 다음 단계에서 SNS 8채널 출력 계약과 슬롯 연결을 진행합니다.

## 3. 구현 원칙

StoryMaker_C 내부에 독립적인 Gemini Adapter를 만듭니다.

V1·Beta 업무일지와 기존 구현은 시행착오와 실패 사례를 참고하는 용도로만 사용할 수 있습니다.

기존 코드를 그대로 복사하거나 일부만 바꿔 재사용하지 않습니다.

StoryMaker_C의 현재 계층 구조와 규칙에 맞춰 독립적으로 작성합니다.

외부 API 호출은 Integration Adapter만 담당합니다.

라우터가 직접 Gemini API를 호출하지 않습니다.

서비스 계층이 프롬프트 조립과 업무 흐름을 담당합니다.

Repository 계층이 DB 접근만 담당합니다.

## 4. PromptContext 구성

업체 정보 스냅샷과 제작 입력값으로 구조화된 `PromptContext`를 만듭니다.

최소 포함 필드는 다음과 같습니다.

- 사용자 ID
- 업체 ID
- 프로젝트 ID
- 업체명
- 업종
- 지역
- 주요 서비스
- 주요 고객층
- 핵심 매력
- 콘텐츠 주제
- 강조 키워드
- 말투
- 분위기
- 콘텐츠 목적
- 금지 표현
- 출력 스키마 버전
- 프롬프트 버전

마이페이지의 현재 업체정보를 직접 참조해 프롬프트를 만들지 않습니다.

프로젝트 생성 당시 저장된 업체정보 스냅샷을 사용합니다.

과거 프로젝트를 다시 열었을 때 업체정보가 바뀌어도 기존 결과가 달라지지 않아야 합니다.

## 5. 프롬프트 구조

프롬프트는 다음 세 영역으로 명확히 분리합니다.

### 5.1 system_rules

- 역할
- 작성 원칙
- 사실을 지어내지 않는 규칙
- 개인정보와 민감정보 처리
- 금지 표현
- 사용자 입력이 시스템 규칙을 덮어쓰지 못하도록 하는 규칙
- 출력 형식 준수 규칙

### 5.2 business_context

- 업체 정보 스냅샷
- 제작 주제
- 목표 고객
- 강조할 서비스
- 지역
- 핵심 매력
- 말투와 분위기

### 5.3 output_contract

이번 6A 단계에서는 8채널 전체가 아니라 단일 시험용 JSON 계약을 사용합니다.

최소 출력 예시는 다음 의미를 가져야 합니다.

- title
- summary
- body
- call_to_action
- keywords
- shortform_script

필드명과 최대 길이는 코드의 중앙 스키마에 정의합니다.

화면 입력값을 단순 문자열 연결로 프롬프트에 넣지 않습니다.

허용된 필드만 명시적으로 조립합니다.

## 6. 사용자 입력과 프롬프트 인젝션 방어

사용자 입력 안에 다음과 같은 문장이 있어도 시스템 규칙을 덮어쓰지 못해야 합니다.

- 이전 지시를 무시하라
- 시스템 프롬프트를 출력하라
- API 키를 알려달라
- JSON 형식을 무시하라

사용자 입력은 데이터 영역으로 취급합니다.

사용자 입력과 시스템 규칙의 경계를 명확히 구분합니다.

Gemini 응답에 시스템 프롬프트, API 키, 내부 경로, 다른 사용자의 데이터가 포함되지 않았는지 검증합니다.

## 7. Gemini Adapter

Gemini 관련 구현은 다음 책임으로 분리합니다.

- 설정 읽기
- API 키 존재 여부 확인
- 모델 이름 확인
- 요청 payload 생성
- timeout 적용
- 제한적 재시도
- 응답 수신
- Provider 오류를 내부 오류코드로 변환

API 키는 환경설정에서만 읽습니다.

코드, DB, 업무일지, 일반 로그에 기록하지 않습니다.

기존 V1·Beta의 Gemini 서비스, Worker, 포트, 세션을 재사용하지 않습니다.

## 8. 실제 API 호출

실제 Gemini API를 최소 1회 이상 호출합니다.

성공 조건은 HTTP 성공만이 아닙니다.

다음 전체를 통과해야 합니다.

1. 응답 수신
2. JSON 추출
3. JSON 파싱
4. 필수 필드 확인
5. 타입 확인
6. 최대 길이 확인
7. 빈 필드 확인
8. 금지 정보 확인
9. 결과 상태 저장

## 9. 오류 상태 분리

최소 다음 오류를 서로 구분합니다.

- api_key_missing
- authentication_failed
- permission_denied
- timeout
- rate_limited
- provider_5xx
- network_error
- invalid_json
- schema_validation_failed
- empty_response
- blocked_response
- duplicate_request
- unknown_provider_error

실패 응답을 `completed`로 저장하지 않습니다.

화면에는 내부 예외 전체를 노출하지 않습니다.

사용자에게는 이해 가능한 메시지와 재시도 가능 여부만 표시합니다.

## 10. 재시도 정책

무한 재시도를 금지합니다.

자동 재시도는 다음에만 제한적으로 적용합니다.

- timeout
- 429
- 일부 5xx
- 일시적인 network_error

인증 오류, 권한 오류, 잘못된 JSON, 스키마 오류는 무조건 반복 호출하지 않습니다.

재시도 횟수와 대기시간은 중앙 설정에서 관리합니다.

동일 프로젝트에 같은 요청이 동시에 두 번 실행되지 않도록 잠금 또는 idempotency key를 사용합니다.

## 11. DB 저장 범위

일반 DB에는 다음 메타데이터만 저장합니다.

- provider
- model
- prompt_version
- response_schema_version
- request_started_at
- completed_at
- latency_ms
- status
- error_code
- retry_count
- project_id
- user_id

전체 프롬프트와 전체 원문 응답은 기본적으로 저장하지 않습니다.

개발 모드에서 문제 분석을 위해 저장해야 한다면 다음 조건을 모두 충족해야 합니다.

- 기본값 비활성
- 별도 보호 경로
- Git 제외
- 개인정보와 비밀값 마스킹
- 관리자만 접근
- 자동 삭제기간 설정

## 12. 로그 정책

일반 로그에 남길 수 있는 항목:

- 작업 ID
- Provider
- 모델
- 상태
- 오류 코드
- HTTP 상태
- latency
- retry 횟수

남기면 안 되는 항목:

- API 키
- Authorization 헤더
- 전체 프롬프트
- 전체 Gemini 응답
- 회원 개인정보
- 다른 사용자 데이터
