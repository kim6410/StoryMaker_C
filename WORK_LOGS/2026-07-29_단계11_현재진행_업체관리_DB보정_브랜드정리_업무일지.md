## 2. 우선순위 1: 업체 관리 완전 정상화 (완료, 철저히 검증됨)

### 2-1. 문제 원인

기존 `/mypage/company`는 사용자당 "기본 업체" 슬롯 1개만 저장/수정하는 구조였다.
이미 업체가 1개 있는 사용자가 폼을 다시 제출하면 **새 업체가 생성되지 않고 기존
업체가 덮어써졌다** - 이것이 "신규 사용자가 실제 업체를 신규 등록하지 못하는 문제"의
정확한 원인이었다. `companies` 테이블 자체는 다중 업체를 저장할 수 있는 구조였지만
애플리케이션 레이어가 단일 슬롯으로만 동작했다.

### 2-2. 구현

- **DB**: 마이그레이션 013으로 `companies`에 세부업종·지역 3단계·도로명/상세주소·
  업체소개·키워드·필수포함·영업시간·네이버플레이스/구글비즈니스 URL·대표이미지
  경로·활성상태 컬럼을 추가(기존 컬럼은 전혀 건드리지 않음). `company_media`
  테이블을 신설해 업체당 콘텐츠용 사진·영상을 여러 개 저장한다. **기본 업체는
  사용자당 정확히 1개**를 부분 UNIQUE 인덱스(`WHERE is_default=1`)로 DB 레벨에서

### 2-4. 이번 검증 중 실제로 발견하고 고친 버그 1건(자체 테스트 스크립트)

임시 E2E 스크립트의 정리 함수가 `sqlite3.connect()`를 직접 호출해 `PRAGMA
foreign_keys=ON`이 적용되지 않은 채로 `companies` 행을 삭제했다. 앱 코드의 실제
`ON DELETE CASCADE`는 정상이었지만, 이 우회 경로 때문에 `company_media`에 부모가
없는 고아 행 6개가 실제로 생겼다(`db_selftest.py`의 `foreign_key_check_empty`가
정확히 이를 잡아냈다). `app.db.connection.get_connection()`(FK 활성화가 보장된
중앙 연결 모듈)으로 고아 행을 정리하고, 이후 정리 함수도 항상 앱의 raw 파일삭제 +
정식 DELETE 순서를 지키도록 재작성했다. 이 사건은 새 지시서가 명시적으로 경고한
"`sqlite3.connect()` 직접 호출" 위험이 실제로 재현된 사례라서 기록해 둔다.

## 4. 시스템 전체에 걸친 POST 리다이렉트 303 버그 일괄 수정

업체관리 라우트를 작성하면서 같은 실수(POST 처리 중 소유권 확인 실패 시
`RedirectResponse(url=...)`에 `status_code`를 지정하지 않아 FastAPI 기본값 307이
적용되고, 브라우저가 리다이렉트를 그대로 POST로 재전송해 405가 나는 문제)를
반복하지 않으려고 전체 파일을 정적 검사했다. 그 결과 이번 세션 이전부터 있던
**기존 코드에도 같은 패턴이 12곳** 남아 있었다(`/content/job/...` 계열 9곳,
`/archive/{uid}/delete` 1곳, `/admin/members/{id}/status` 1곳, 그리고 업체관리
신규 코드 6곳). 전부 `status_code=303`으로 통일하고, 실제 HTTP 요청으로 재현 테스트
(로그인 안 한 상태 POST, 소유권 없는 POST 모두 405가 아니라 정상 303→200으로
이어짐)까지 확인했다.
