## 2. 핵심 발견

1. **대시보드·보관함(목록/상세)은 0단계 클릭형 샘플 그대로**이고, 단계 5~9에서 만든 실제 데이터(프로젝트/8채널/TTS/SRT/MP4)와 전혀 연결돼 있지 않다. 이번 단계의 가장 큰 작업은 이 3화면을 실데이터로 재구현하는 것이다.
2. 제작 흐름(새 콘텐츠 → 상태 → 채널 → TTS → MP4)은 각 URL이 독립 페이지라 사용자가 지금 몇 단계인지, 다음에 뭘 해야 하는지 화면만 봐서는 알기 어렵다 → 공통 단계표시기 컴포넌트가 필요하다.
3. `.btn.danger` 스타일이 없다 — 삭제 등 위험 동작을 위한 시각 구분이 없다.
4. Range 재생은 단계9에서 서버 쪽은 이미 고쳤으니(2026-07-29 단계9 업무일지 3번), 이번 단계는 화면에서 실제로 탐색(seek)이 되는지 사용자 관점으로 재확인만 하면 된다.

## 3. 구현 계획(우선순위)

1. 공통 단계표시기 컴포넌트(`_step_indicator.html` 매크로) + `projects.status` 기반 8단계 매핑, 5개 제작 페이지에 삽입
2. 대시보드 실데이터 전환(최근 작업 5개, 진행중/실패/완성 카운트, 이번달 사용량, 빈 상태 화면)
3. 보관함 목록·상세 실데이터 전환(완성된 프로젝트만, 필터, 결과물 링크)
4. 제작 입력화면 보강(필수/선택 표시, 예시 문구, 브라우저 임시저장으로 새로고침 복구)
5. 8채널/TTS/MP4 화면 다듬기(상태 문구 통일, danger 버튼, 삭제/재생성 확인모달, 전화번호 TTS 미리듣기)
6. 디자인 토큰 보강(`.btn.danger`, 상태색 통일)
7. 실브라우저 E2E(신규 사용자 전체 흐름, 반응형 3종, 접근성 기본)
8. 회귀 확인(단계6~9 API 계약 무변경 확인) + DB 무결성 + 외부경로 재검사
9. 업무일지 작성 → 선별 커밋 → Push → 해시 확인

기존 6~9단계 라우트/서비스 계층의 요청·응답 계약은 변경하지 않고, 화면(템플릿)과 신규 조회 전용 쿼리만 추가한다.
