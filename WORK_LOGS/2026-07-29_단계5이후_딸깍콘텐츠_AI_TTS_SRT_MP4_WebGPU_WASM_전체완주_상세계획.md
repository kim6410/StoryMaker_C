## 2. 가장 중요한 개발 원칙

새 기능을 붙일 때 기존 인증, DB, 업체 정보, 관리자 기능을 직접 수정하며 얽히게 만들지 않습니다.

각 기능은 분리된 모듈과 명확한 입력·출력 계약을 사용합니다.

권장 책임 구분은 다음과 같습니다.

- `app/content`: 제작 요청, 입력 검증, 콘텐츠 작업 상태
- `app/ai`: 프롬프트 구성, Provider 호출, 응답 검증
- `app/tts`: 음성 생성 요청과 결과 관리
- `app/subtitle`: 문장 분할, 타임라인, SRT 생성
- `app/media`: 이미지·영상 정규화, 오디오 믹싱, MP4 렌더링
- `app/archive`: 보관함 저장, 조회, 다운로드, 삭제 정책
- `app/jobs`: 작업 큐, 잠금, 재시도, 복구
- `app/integrations`: Gemini, WordPress, SMTP 등 외부 서비스 Adapter

라우터는 요청과 응답만 담당합니다.

서비스는 업무 규칙만 담당합니다.

Repository는 DB 접근만 담당합니다.

외부 API 호출은 Integration Adapter만 담당합니다.

템플릿과 JavaScript가 회원 권한, 구독 한도, 작업 완료 여부를 임의로 결정하지 않습니다.

## 3. 단계 5: 새 딸깍 콘텐츠 제작 입력 화면

마이페이지의 업체 정보를 새 콘텐츠 제작 화면에서 기본값으로 불러옵니다.

사용자는 다음 항목을 확인하거나 이번 작업에 한해서만 수정할 수 있어야 합니다.

- 업체명
- 대표자 또는 담당자
- 전화번호
- 업종
- 지역
- 주요 서비스
- 주요 고객층
- 핵심 매력
- 콘텐츠 주제
- 강조할 키워드
- 말투와 분위기
- 콘텐츠 길이
- 사용할 사진과 영상
- 배경음악
- 음성 화자

업체 정보 원본과 제작 당시 입력값을 분리합니다.

마이페이지 업체 정보를 바꾸지 않고, 제작 작업에는 당시 입력 스냅샷을 저장합니다.

작업이 나중에 다시 열렸을 때 업체 정보가 변경돼도 과거 결과가 달라지지 않도록 해야 합니다.

제작 요청 시 작업 상태는 최소 다음 순서를 사용합니다.

`draft → queued → prompting → generating → validating → content_ready → tts_ready → subtitle_ready → media_ready → rendering → completed`

실패 시에는 `failed` 상태와 단계별 오류 코드를 함께 저장합니다.

## 4. 프롬프트 생성과 Gemini 전송 방법

Gemini에 화면의 입력값을 그대로 뒤섞어 보내지 않습니다.

먼저 서버에서 구조화된 제작 컨텍스트를 만듭니다.

제작 컨텍스트에는 다음 정보만 포함합니다.

- 업체 정보 스냅샷
- 사용자가 선택한 주제와 키워드
- 목표 고객
- 콘텐츠 목적
- 채널별 형식
- 금지 표현
- 결과 JSON 스키마

프롬프트는 세 부분으로 나눕니다.

### 시스템 규칙

역할, 작성 원칙, 사실을 지어내지 않는 규칙, 금지 표현, 개인정보 처리, 출력 형식을 정의합니다.

### 업체·작업 컨텍스트

업체명, 업종, 지역, 주요 서비스, 고객층, 핵심 매력, 이번 주제를 전달합니다.

### 출력 계약

Gemini가 반드시 정해진 JSON 구조로 응답하도록 요구합니다.

권장 결과 슬롯은 다음과 같습니다.

1. 네이버 블로그
2. 인스타그램
3. 페이스북
4. 당근
5. 네이버 플레이스
6. 구글 비즈니스 프로필
7. 카카오채널 또는 짧은 안내문
8. 숏폼 영상 원고

각 슬롯은 최소 다음 속성을 가집니다.

- 채널 코드
- 제목
- 본문
- 해시태그
- 짧은 CTA
- 복사용 HTML이 필요한 경우 HTML
- 영상용 장면 문장 목록
- 음성용 원고

Gemini 응답은 바로 화면에 꽂지 않습니다.

다음 검증을 통과해야 합니다.

- JSON 파싱 성공
- 8개 채널 누락 없음
- 필수 필드 존재
- 문자열 최대 길이 준수
- 비어 있는 슬롯 없음
- 업체명·전화번호 오염 여부
- 다른 업체 정보 혼입 여부
- 금지 표현 여부
- HTML 허용 태그 검사

검증 실패 시 전체를 반복 호출하기보다 누락 슬롯만 보정 요청하는 구조를 권장합니다.

API 키, 전체 프롬프트, 전체 응답은 일반 로그에 남기지 않습니다.

오류 로그에는 Provider, 모델, 작업 ID, HTTP 상태, 오류 코드, 소요 시간만 남깁니다.

## 5. SNS 8채널 슬롯 연결

AI 검증이 끝나면 서버 DB에 채널별 결과를 별도 행으로 저장합니다.

화면은 DB에 저장된 결과를 읽어 슬롯에 표시합니다.

브라우저 메모리에만 결과를 보관하지 않습니다.

각 슬롯에는 다음 기능이 필요합니다.

- 제목과 본문 표시
- 복사
- HTML 복사
- 부분 수정
- 원본으로 되돌리기
- 채널 하나만 재생성
- 저장 상태 표시
- 생성 시각과 수정 시각

슬롯 하나의 수정이나 재생성이 다른 7개 슬롯을 덮어쓰지 않도록 합니다.

## 6. TTS 생성 방법

TTS는 콘텐츠 생성과 분리된 독립 단계로 둡니다.

먼저 영상용 원고를 문장 또는 장면 단위로 정규화합니다.

다음 항목을 결정합니다.

- 화자
- 속도
- 감정 또는 톤
- 문장 사이 쉼
- 숫자와 전화번호 읽기 방식
- 영어·기호 발음 처리

Supertonic을 사용할 경우 StoryMaker_C 전용 실행 파일, 모델, 캐시, 로그, 포트를 사용합니다.

기존 V1·Beta의 실행 중 서비스에 직접 요청하지 않습니다.

TTS 결과는 문장별 개별 WAV와 전체 합성 WAV를 모두 보관할 수 있습니다.

문장별 WAV는 자막 싱크와 재시도에 유리합니다.

전체 TTS 실패 시 처음부터 모든 문장을 다시 만들지 않고 실패 문장만 재생성할 수 있어야 합니다.

## 7. SRT 생성 방법

가장 정확한 방법은 문장별 TTS 파일의 실제 길이를 기준으로 타임라인을 만드는 것입니다.

전체 음성 길이를 글자 수로 임의 분배하지 않습니다.

절차는 다음과 같습니다.

1. 영상 원고를 자막 문장으로 분할
2. 문장별 TTS 생성
3. 각 WAV 실제 재생시간 측정
4. 문장 사이 쉼 시간 반영
5. 누적 시작·종료 시간 계산
6. SRT 작성
7. 전체 음성과 SRT 종료 시각 비교

자막에는 `[여성]`, `[남성]` 같은 화자 표시를 넣지 않습니다.

한 화면에 너무 긴 문장이 나오지 않도록 글자 수와 줄 수를 제한합니다.

## 8. 배경음악과 음성 혼합

원본 음성과 음악을 직접 덮어쓰지 않습니다.

다음 산출물을 분리해서 보관합니다.

- 원본 음성
- 선택된 배경음악
- 음악 볼륨 조정본
- 최종 혼합 음성

음악은 음성이 들릴 때 자동으로 낮아지는 Ducking 처리를 적용할 수 있습니다.

기본 원칙은 음성 명료도가 음악보다 우선입니다.

최종 MP4는 반드시 최종 혼합 음원을 사용합니다.

## 9. 이미지와 영상 입력 정규화

사용자가 올린 파일을 렌더러에 바로 넘기지 않습니다.

먼저 다음을 검사합니다.

- 확장자와 실제 MIME 일치
- 이미지 크기
- 영상 코덱
- 재생시간
- 회전 메타데이터
- 손상 여부
- 최대 파일 크기

모든 미디어는 프로젝트 내부 작업 폴더로 복사한 뒤 작업 ID 아래에서 관리합니다.

원본과 렌더용 변환본을 분리합니다.

## 10. 화면 전환, 줌인·줌아웃, 움직임

각 장면은 이미지 또는 영상, 시작시간, 종료시간, 전환, 움직임 값을 가집니다.

권장 전환은 과하지 않게 제한합니다.

- 페이드
- 크로스 디졸브
- 슬라이드
- 밝기 전환

줌인·줌아웃은 이미지의 중심점과 확대 비율을 정의합니다.

예를 들어 한 장면에서 100%에서 110%로 천천히 확대하거나, 112%에서 100%로 축소하는 방식입니다.

모든 장면에 서로 다른 화려한 효과를 넣지 않습니다.

장면 전환은 음성 문장 경계와 맞추는 것이 좋습니다.

## 11. FFmpeg 서버 렌더링

안정적인 최종 렌더 기준은 FFmpeg 서버 렌더입니다.

처리 순서는 다음과 같습니다.

1. 이미지·영상 정규화
2. 장면별 해상도와 프레임레이트 통일
3. 줌과 이동 적용
4. 장면 전환 연결
5. SRT 자막 오버레이
6. 상호·전화번호 오버레이
7. 혼합 음성 결합
8. H.264와 AAC로 MP4 출력
9. 파일 크기, 길이, 코덱, 재생 가능 여부 검증

숏폼 기본 비율은 9:16으로 하고, 필요 시 16:9를 별도 렌더 프리셋으로 둡니다.

## 12. WASM과 WebGPU를 활용한 사용자 PC 자원 사용

브라우저에서 사용자 PC 자원을 활용하면 서버 부하를 줄일 수 있습니다.

다만 처음부터 브라우저 렌더만 유일한 방식으로 두지 않습니다.

안정적인 권장 구조는 다음입니다.

- 서버 FFmpeg 렌더: 최종 신뢰 가능한 기본 방식
- 브라우저 WASM·WebCodecs·WebGPU 렌더: 선택 가능한 가속 방식
- 브라우저 가속 실패 시 서버 렌더 폴백

### WASM 활용

WASM은 브라우저에서 다음 작업에 활용할 수 있습니다.

- 오디오 파형 분석
- 간단한 음량 정규화
- 이미지 리사이즈
- 미디어 메타데이터 분석
- ffmpeg.wasm 기반의 제한적 인코딩

ffmpeg.wasm은 큰 파일과 긴 영상에서 메모리 사용량이 커질 수 있으므로 짧은 숏폼과 미리보기에 적합합니다.

### WebGPU 활용

WebGPU는 다음 작업에 활용할 수 있습니다.

- 이미지 합성
- 색상 보정
- 블러와 그림자
- 장면 전환
- 줌인·줌아웃
- 텍스트·자막 렌더링
- 프레임 생성

WebGPU는 GPU에서 프레임을 만들고, WebCodecs를 통해 비디오 인코딩하는 구조가 효율적입니다.

지원 여부는 실행 전에 확인합니다.

미지원 브라우저, GPU 차단, 드라이버 문제, 메모리 부족 시 자동으로 서버 렌더를 안내하거나 전환합니다.

### 로컬 렌더 작업 흐름

1. 서버가 작업 명세 JSON과 허용된 미디어 URL을 전달
2. 브라우저가 미디어를 내려받음
3. WebGPU로 프레임 합성
4. WebCodecs로 영상 인코딩
5. WASM 또는 Web Audio로 오디오 처리
6. MP4 컨테이너 조립
7. 완성 파일 검증
8. 사용자가 승인하면 서버 보관함으로 업로드

브라우저 렌더 중 탭이 닫히면 작업이 중단될 수 있으므로 진행률과 재시작 안내가 필요합니다.

## 13. 썸네일 생성

MP4 완성 후 영상과 업체 정보를 바탕으로 9:16 썸네일 8종을 생성합니다.

가능한 방법은 두 가지입니다.

- 브라우저 Canvas·WebGPU 템플릿 생성
- 이미지 AI Provider 생성

처음에는 빠르고 예측 가능한 브라우저 템플릿 방식을 기본으로 권장합니다.

8개 미리보기는 브라우저에서 만들고, 사용자가 선택한 1개만 서버에 저장하는 구조가 저장공간 측면에서 유리합니다.

## 15. 작업 큐, 잠금, 재시도, 복구

한 작업이 동시에 두 번 실행되지 않도록 작업별 잠금을 사용합니다.

서버 재시작 후에도 `processing` 상태에 멈춘 작업을 탐지하고 복구할 수 있어야 합니다.

단계별 산출물이 이미 정상이라면 재사용하고, 깨진 단계부터 다시 시작합니다.

예를 들어 콘텐츠와 음성이 이미 정상이고 MP4만 실패했다면 Gemini와 TTS를 다시 호출하지 않습니다.

## 20. McKinsey 참고 디자인 고도화 가이드 — 우선 적용

이 항목은 이후 화면 기능을 추가하거나 수정할 때 먼저 적용하는 공통 디자인 원칙입니다.

참고 대상은 McKinsey 웹사이트의 현재 정보 구조와 시각적 태도입니다. McKinsey의 로고, 문구, 이미지, 레이아웃을 그대로 복제하지 않습니다. 대신 큰 제목과 짧은 보조문장, 넉넉한 여백, 명확한 콘텐츠 위계, 절제된 강조색, 카드보다 섹션 중심의 구성, 읽는 흐름이 자연스러운 편집형 레이아웃을 참고합니다.

현재 StoryMaker_C의 어두운 테마와 좌측 메뉴 구조는 유지하되, 화면이 개발자용 관리자 패널처럼 보이지 않고 신뢰감 있는 비즈니스 도구처럼 보이도록 다듬습니다.

### 20-1. 최우선 디자인 방향

- 한 화면에서 가장 중요한 행동은 하나만 강하게 보이게 합니다.
- 모든 카드에 동일한 테두리와 배경을 반복하지 않습니다.
- 카드 안에 카드를 중첩하지 않습니다.
- 페이지 제목, 설명, 핵심 행동, 보조 정보 순서가 한눈에 보이게 합니다.
- 숫자 카드와 상태 정보는 장식보다 의미 전달을 우선합니다.
- 파란색 강조는 CTA, 선택 상태, 링크, 진행 단계에만 제한적으로 사용합니다.
- 노란색과 초록색은 경고·완료 같은 상태 의미에만 사용합니다.
- 화면 전체에 그라데이션, 유리 효과, 네온, 반짝임, 과한 그림자를 사용하지 않습니다.
- AI 서비스 특유의 보라색 그라데이션과 유동형 배경은 사용하지 않습니다.
- 사용자가 읽고 판단해야 하는 화면은 편집 기사처럼 여백과 타이포그래피로 정리합니다.
- 사용자가 입력하고 실행해야 하는 화면은 업무 도구처럼 명확한 폼 구조와 단계 안내를 제공합니다.

### 20-2. 타이포그래피

- 페이지 최상단 제목은 현재보다 크고 단단하게 사용합니다.
- 제목 아래 설명은 한두 문장으로 제한하고 너비를 지나치게 넓히지 않습니다.
- 본문, 도움말, 상태 문구의 크기 차이를 분명하게 둡니다.
- 카드 숫자, 플랜명, 제작 상태는 같은 크기로 반복하지 않고 중요도에 따라 차등을 둡니다.
- 한글 본문은 지나치게 굵게 사용하지 않습니다.
- 영문 브랜드명과 숫자는 자간이 무너지지 않도록 확인합니다.
- 줄 길이는 PC 기준 약 55~80자 범위를 권장합니다.
- 설명이 긴 경우 전체 폭을 사용하지 않고 읽기 좋은 최대 너비를 둡니다.

### 20-3. 색상과 대비

현재 다크 테마를 유지하되 배경 단계는 세 수준 정도로 단순화합니다.

- 최상위 배경
- 섹션 배경
- 입력·선택 요소 배경

모든 영역을 서로 다른 남색으로 칠하지 않습니다.

테두리는 화면 구획이 필요한 곳에만 사용합니다.

본문 색상, 보조 텍스트, 비활성 텍스트의 대비 차이를 명확하게 합니다.

주요 버튼은 현재의 밝은 하늘색 계열을 사용할 수 있으나, 한 화면에 강한 버튼은 한두 개로 제한합니다.

### 20-4. 페이지 공통 레이아웃

모든 페이지는 아래 순서를 기본으로 합니다.

1. 페이지 제목
2. 짧은 설명
3. 현재 상태 또는 핵심 행동
4. 주요 작업 영역
5. 보조 정보
6. 도움말·정책·주의사항

상단 제목과 첫 콘텐츠 사이 간격을 일정하게 유지합니다.

좌측 메뉴 폭과 상단 헤더 높이를 고정하고, 콘텐츠 영역의 최대 너비를 화면마다 제각각 만들지 않습니다.

넓은 화면에서는 모든 콘텐츠를 끝까지 늘리지 않고 적절한 최대 너비를 둡니다.

모바일에서는 좌측 메뉴를 접을 수 있는 구조로 바꾸고, 핵심 버튼이 화면 하단에 묻히지 않도록 합니다.

### 20-5. 대시보드

현재 대시보드는 숫자 카드가 동일한 비중으로 네 개 나열되어 있습니다.

다음 방향으로 고도화합니다.

- 가장 중요한 정보는 이번 달 남은 제작 가능 횟수로 둡니다.
- 누적 제작 수와 보관함 유지 개수는 보조 정보로 낮춥니다.
- 숫자 카드 네 개를 동일 크기로 반복하기보다 핵심 지표 하나와 보조 지표 묶음으로 재구성합니다.
- 빠른 시작 영역은 큰 CTA 하나와 짧은 설명으로 단순화합니다.
- 최근 보관함은 표보다 제목, 업체, 상태, 날짜가 빠르게 읽히는 리스트 구조를 우선 검토합니다.
- 최근 작업이 없을 때는 빈 표 대신 제작 시작을 유도하는 빈 상태 화면을 표시합니다.
- 알림 종 아이콘은 읽지 않은 공지 수가 있을 때만 강조합니다.
- 관리자 팝업 공지와 일반 알림을 같은 UI에서 혼동하지 않게 구분합니다.

권장 대시보드 위계:

`남은 제작 가능 횟수 → 새 콘텐츠 제작 → 최근 작업 → 보관 정책·공지`

### 20-6. 새 콘텐츠 제작 화면

현재 단계 탭과 입력 폼 구조는 유지하되 다음을 적용합니다.

- 상단 단계 표시는 작고 간결하게 유지합니다.
- 현재 단계만 강하게 표시하고 완료 단계는 체크 상태로 바꿉니다.
- 경고 문구는 큰 노란 테두리 상자 대신 짧은 인라인 안내와 마이페이지 이동 버튼으로 정리합니다.
- 업체 정보 입력은 필수·선택 항목을 명확히 구분합니다.
- 필드 설명을 라벨과 입력창 사이에 과도하게 반복하지 않습니다.
- 주요 고객층, 핵심 매력, 말투처럼 긴 입력은 넓은 한 열 구조를 사용합니다.
- 저장·다음 단계 버튼은 화면 하단의 일관된 위치에 둡니다.
- 사용자가 입력하지 않아도 되는 자동값은 읽기 전용 요약 카드로 보여줍니다.
- 배경음악 선택은 파일명 나열보다 재생, 분위기, 길이, 추천 업종을 함께 보여줍니다.

### 20-7. SNS 8채널 결과 화면

- 8개 슬롯을 동일한 긴 카드로 한 화면에 전부 펼치지 않습니다.
- 채널 탭 또는 좌측 채널 목록과 우측 편집 영역 조합을 권장합니다.
- 채널별 상태를 `완료`, `수정됨`, `재생성 중`, `오류`로 명확히 표시합니다.
- 복사, HTML 복사, 저장, 재생성 버튼의 우선순위를 구분합니다.
- 가장 자주 쓰는 복사 버튼을 주요 행동으로 둡니다.
- 긴 본문은 읽기 모드와 편집 모드를 분리합니다.
- AI 생성 결과임을 과하게 강조하지 않고, 사용자가 최종 편집하는 업무 결과물처럼 보이게 합니다.

### 20-8. 보관함

현재 큰 빈 썸네일 카드가 반복되는 구조는 실제 데이터가 없을 때 화면이 지나치게 비어 보입니다.

다음 방향을 적용합니다.

- 썸네일이 없는 작업은 의미 있는 기본 이미지와 작업 상태를 표시합니다.
- 카드 높이를 줄여 한 화면에서 더 많은 작업을 확인할 수 있게 합니다.
- 제목, 업체명, 제작일, 상태, 대표 썸네일을 명확한 순서로 배치합니다.
- 검색과 정렬은 한 줄에 유지합니다.
- PC에서는 카드·리스트 전환을 지원할 수 있습니다.
- 자동정리 예정 항목은 과한 경고 대신 날짜와 보존 버튼을 제공합니다.
- 상세 화면은 콘텐츠, 음성, SRT, MP4, 썸네일을 탭으로 나눕니다.

### 20-9. 마이페이지

- 업체 정보와 계정 정보를 탭으로 나눈 현재 구조는 유지합니다.
- 폼 전체를 큰 카드 하나에 넣되, 논리적 섹션 사이에 여백과 소제목을 사용합니다.
- 두 열 폼은 서로 연관된 짧은 값에만 사용합니다.
- 주소, 주요 서비스, 고객층, 핵심 매력은 한 열 전체 폭을 사용합니다.
- 저장 버튼은 폼 시작과 멀리 떨어지지 않도록 하단 고정 또는 명확한 종료 지점에 둡니다.
- 저장 성공은 토스트만 띄우지 말고 버튼 주변에 짧게 상태를 표시합니다.

### 20-10. 구독 및 사용량

- 현재 플랜, 남은 사용량, 보관함 한도를 가장 먼저 보여줍니다.
- Free, Starter, Standard를 단순 가격표처럼 동일하게 나열하지 않습니다.
- 현재 플랜은 별도 요약 영역으로 분리합니다.
- 업그레이드 가능한 플랜은 혜택 차이가 실제로 확정된 뒤 비교합니다.
- Starter와 Standard의 혜택 차이가 정의되지 않았다면 판매 버튼을 활성화하지 않습니다.
- 보관기간, 자동정리 예정일, 다운로드 가능 기간을 쉬운 문장으로 설명합니다.
- 가격보다 사용자가 얻게 되는 차이를 먼저 보여줍니다.

### 20-11. 관리자 화면과 팝업 공지

- 실제 게시 전 PC·모바일 미리보기를 제공합니다.
- 공지 성과가 필요하면 노출 수, 닫기 수, 버튼 클릭 수를 별도 집계합니다.

- 비동기 작업 중 같은 버튼을 중복 클릭하지 못하게 합니다.
- 카드 hover 효과는 마우스가 있는 PC에서만 약하게 사용합니다.
- 폼 오류는 상단 전체 경고와 해당 필드 오류를 함께 제공합니다.
- 스켈레톤 로딩은 실제 데이터 로딩이 있는 영역에만 사용합니다.

## 21. 배경음악 MP3 이관 완료와 관리 지시

배경음악 원본은 사용자 승인에 따라 아래 경로에서 읽기 전용으로 복사했습니다.

- 원본: `F:\StoryMaker_beta\media\music`
- 대상: `F:\StoryMaker_C\runtime\music\mp3`
- 복사 파일 수: 61개
- 총용량: 253,826,053 bytes

원본 폴더와 파일은 수정·이동·삭제하지 않았습니다.

앞으로 StoryMaker_C는 복사된 대상 폴더만 사용합니다.

클로드는 단계 8 배경음악 기능을 구현하기 전에 아래 작업을 수행합니다.

1. `F:\StoryMaker_C\runtime\music\mp3` 아래 파일 목록을 읽어 음악 카탈로그를 만듭니다.
2. 파일명, 상대경로, 크기, SHA-256, 재생시간, 코덱, 비트레이트, 샘플레이트를 수집합니다.
3. 같은 SHA-256 파일은 중복 후보로 표시하되 자동 삭제하지 않습니다.
4. `(1)` 같은 중복 추정 이름도 해시가 다르면 유지합니다.
5. 파일명을 바로 변경하지 말고 DB에는 표시용 제목과 실제 상대경로를 분리합니다.
6. 장르·분위기·속도·추천 업종·추천 영상 길이를 관리할 수 있는 음악 메타데이터 구조를 만듭니다.
7. 기본 카테고리는 밝음, 감성, 잔잔함, 신나는 분위기, 고급스러움, 스포츠, 키즈, 로맨틱, 클래식, 힙합, 기타로 시작할 수 있습니다.
8. 관리자가 음악 활성화 여부, 표시 순서, 기본 볼륨, 추천 카테고리를 수정할 수 있게 설계합니다.
9. 원본 MP3는 읽기 전용 자산으로 취급하고, 볼륨 조절·길이 자르기·페이드 처리는 작업별 임시 사본에서만 수행합니다.
10. 최종 MP4에는 선택된 음악의 작업용 사본과 최종 혼합 음원을 사용합니다.
11. 음악 파일 경로는 DB에 `runtime/music/mp3/...` 형태의 프로젝트 상대경로로 저장합니다.
12. 프로젝트 밖의 V1·Beta 음악 경로를 코드·DB·설정에 남기지 않습니다.

클로드가 음악 폴더를 다른 내부 위치로 재배치해야 한다고 판단하면 먼저 새 구조와 참조 변경 범위를 보고합니다.

이동은 `F:\StoryMaker_C` 내부에서만 허용하며, 참조 수정·해시 검증·재생 테스트가 끝난 뒤에만 기존 내부 위치를 정리합니다.

## 22. 회원등급과 현재 확인된 플랜 기준

현재 화면과 기존 확정 문서에서 확인되는 회원등급 기준은 다음과 같습니다.

### Free

- 가격: 0원
- 월 콘텐츠 제작 한도: 20회
- 보관함 한도: 최신 10개
- 기본 회원가입 후 적용되는 플랜

### Starter

- 현재 화면 표시 가격: 월 29,000원
- 월 콘텐츠 제작 한도: 현재 화면 기준 20회
- 보관함 한도: 최신 20개
- Free보다 넓은 보관함 제공
- 업체 정보, SNS 8채널, 음성, SRT, MP4, 썸네일, 보관함 기능을 정식 제공하는 기본 유료 플랜으로 설계
- 파일 보존 잠금, 대표 썸네일 저장, 완성 결과 ZIP 또는 통합 다운로드 같은 유료 혜택을 붙일 수 있는 구조로 설계

### Standard

현재 샘플 화면에는 월 59,000원, 월 제작 20회, 보관함 최신 20개로 표시되어 있습니다.

Starter와 차이가 정의되지 않았으므로 실제 과금 기능을 구현하기 전에 별도 정책 확정이 필요합니다.

차이가 확정되지 않은 상태에서 Standard를 실제 판매 플랜으로 활성화하지 않습니다.

### 플랜 정책 구현 원칙

플랜 이름, 가격, 월 제작 한도, 보관함 개수, 파일 보관기간, 최대 업로드 크기, 영상 길이, 동시 작업 수를 HTML이나 Python 여러 곳에 하드코딩하지 않습니다.

`subscription_plans` 또는 별도 정책 테이블 한 곳에서 관리합니다.

사용량은 서버에서 실제 사용자와 해당 월을 기준으로 계산합니다.

브라우저 표시값만으로 제작을 허용하거나 차단하지 않습니다.

관리자는 플랜별 값을 수정할 수 있지만, 변경 이력과 적용 시점을 감사로그에 남겨야 합니다.

기존 가입자의 현재 구독기간 중 정책을 즉시 변경할지 다음 갱신일부터 적용할지도 구분합니다.

## 23. 파일 저장기간과 자동정리 정책

현재 확정된 기준은 Free 최신 10개, Starter 최신 20개라는 개수 제한입니다.

일 단위 보관기간은 아직 최종 확정된 값이 없으므로 임의로 운영 삭제를 시작하지 않습니다.

개발 구조는 아래처럼 개수 제한과 기간 제한을 모두 지원하도록 만듭니다.

- `archive_item_limit`: 보관 가능한 항목 수
- `retention_days`: 자동정리까지의 일수
- `grace_days`: 정리 예정 안내 후 실제 삭제까지의 유예기간
- `locked_item_limit`: 사용자가 보존 잠금할 수 있는 개수
- `trash_retention_days`: 휴지통에서 완전 삭제되기 전 보관기간

사용자 승인 전 권장 초깃값은 정책 예시로만 두고 실제 삭제 기능은 비활성화합니다.

- Free 예시: 최신 10개, 30일 보관, 7일 유예
- Starter 예시: 최신 20개, 90일 보관, 14일 유예

위 기간값은 확정값이 아니며 관리자 설정 화면에서 변경 가능하게 만듭니다.

자동정리는 다음 순서를 지킵니다.

1. 매일 정해진 시간에 정리 후보만 계산합니다.
2. 보존 잠금된 항목은 제외합니다.
3. 진행 중, 실패 복구 중, 결제 분쟁 중, 관리자 보존 항목은 제외합니다.
4. 플랜의 개수 한도와 보관기간을 모두 검사합니다.
5. 가장 오래된 일반 항목부터 `cleanup_scheduled` 상태로 전환합니다.
6. 사용자에게 삭제 예정일을 표시합니다.
7. 유예기간 동안 사용자가 다운로드, 보존 잠금 또는 직접 삭제할 수 있게 합니다.
8. 유예기간 종료 후 먼저 휴지통 상태로 전환합니다.
9. 휴지통 보관기간이 지난 뒤 실제 파일을 제거합니다.
10. DB 행은 즉시 지우지 않고 삭제 감사기록과 파일 해시를 남깁니다.
11. 파일 삭제가 성공한 경우에만 DB의 삭제 완료 상태를 기록합니다.
12. 일부 파일 삭제가 실패하면 완료로 표시하지 않고 재시도 대상으로 남깁니다.

자동정리 대상에는 작업별 임시파일, 중간 WAV, 렌더 캐시도 포함할 수 있습니다.

완성 MP4, SRT, 대표 썸네일, SNS 8채널 결과는 사용자 보관 정책에 따라 처리하고, 임시파일은 더 짧은 기간으로 별도 관리합니다.

권장 분리는 다음과 같습니다.

- `temp`: 작업 완료 또는 실패 후 짧은 기간 내 정리
- `cache`: 재생성 가능한 파일, 용량 정책에 따라 정리
- `outputs`: 사용자 보관 정책 적용
- `imports/quarantine`: 자동정리 금지, 관리자 승인으로만 정리
- `logs`: 개인정보 마스킹 후 로그 보존정책 적용

사용자가 플랜을 낮추더라도 즉시 파일을 삭제하지 않습니다.

초과 항목을 정리 예정으로 표시하고 다운로드와 보존 선택을 위한 유예기간을 제공합니다.

## 24. 관리자 팝업 공지 기능

관리자 페이지에 사용자 공지 팝업 관리 기능을 추가합니다.

- 공지 제목
- 공지 본문
- 선택 이미지
- 버튼 문구
- 버튼 연결 주소
- 게시 시작 일시
- 게시 종료 일시
- 팝업 지속시간 또는 자동 닫힘 시간
- 사용자가 직접 닫을 수 있는지 여부
- 오늘 하루 보지 않기 허용 여부
- 다시 보지 않기 허용 여부
- 로그인 화면, 대시보드, 제작 화면, 보관함 등 노출 위치
- 전체 사용자 또는 특정 플랜·역할 대상
- PC, 모바일 또는 전체 기기
- 우선순위
- 활성·비활성 상태

여기서 게시 지속기간과 화면 표시 지속시간을 분리합니다.

- 게시 시작·종료: 공지가 사용자에게 노출되는 전체 기간
- 자동 닫힘 시간: 한 번 화면에 나타난 팝업이 자동으로 닫히기까지의 초 단위 시간

자동 닫힘은 0으로 설정하면 자동으로 닫히지 않도록 합니다.

관리자는 미래 시각 예약 게시와 즉시 게시를 모두 사용할 수 있어야 합니다.

공지 DB는 최소 다음 정보를 가집니다.

- 공지 ID
- 제목과 본문
- 이미지 상대경로
- 버튼 문구와 URL
- 시작·종료 시각
- 자동 닫힘 초
- 대상 역할과 플랜
- 노출 페이지
- 기기 범위
- 우선순위
- 활성 상태
- 작성 관리자 ID
- 생성·수정 시각
- 마지막 게시 시각

사용자별 표시 기록도 별도 저장합니다.

- 사용자 ID 또는 익명 브라우저 식별자
- 공지 ID
- 최초 표시 시각
- 마지막 표시 시각
- 표시 횟수
- 닫은 시각
- 오늘 하루 보지 않기 만료 시각
- 다시 보지 않기 여부

팝업 본문은 허용된 HTML만 사용하거나 안전한 Markdown을 서버에서 정화한 뒤 표시합니다.

관리자가 임의 JavaScript, iframe, script 태그를 입력할 수 없도록 합니다.

버튼 URL도 `javascript:` 같은 위험한 스킴을 차단합니다.

사용자 화면에서는 서버가 현재 시각, 대상 플랜, 역할, 페이지, 사용자별 숨김 상태를 검사한 뒤 표시할 공지만 전달합니다.

브라우저 JavaScript만으로 대상 여부를 결정하지 않습니다.

동시에 여러 공지가 활성화되면 우선순위가 높은 하나만 먼저 표시하거나 관리자 설정에 따라 순차 표시합니다.

팝업이 제작 중인 입력값이나 렌더 진행을 방해하지 않도록 제작 진행 화면에서는 표시 시점과 크기를 제한합니다.

관리자 화면에는 미리보기, 예약 상태, 현재 게시 중, 종료, 비활성 상태를 구분해 표시합니다.

공지 생성·수정·삭제·게시 시작·게시 중단은 모두 감사로그에 남깁니다.

중요 POST 요청에는 CSRF와 관리자 권한 검사를 적용합니다.

## 25. 추가 단계와 완주 기준 반영

기존 단계 11의 관리자 모니터링 범위에 다음을 추가합니다.

- 회원 플랜과 사용량 정책 관리
- 파일 보관기간과 자동정리 정책 관리
- 정리 예정·휴지통·삭제 실패 목록
- 음악 카탈로그와 활성화 관리
- 사용자 팝업 공지 작성·예약·중단·미리보기

추가 자동 테스트는 다음과 같습니다.

- Free 사용자의 11번째 보관 항목 처리
- Starter 사용자의 21번째 보관 항목 처리
- 보존 잠금 항목 자동정리 제외
- 유예기간 전 실제 파일 미삭제
- 휴지통 기간 전 완전 삭제 금지
- 파일 삭제 실패 시 DB 완료 처리 금지
- 플랜 하향 시 즉시 삭제 금지
- 예약 공지가 시작 전에는 보이지 않음
- 시작 시각 이후 대상 사용자에게만 표시
- 종료 시각 이후 표시되지 않음
- 자동 닫힘 0과 지정 초 동작
- 오늘 하루 보지 않기 만료 처리
- 다른 플랜·역할 사용자에게 공지 미노출
- 일반 사용자의 관리자 공지 API 접근 차단
- 팝업 HTML과 URL 보안 검사
- 음악 61개 카탈로그 등록과 해시 검증
- 원본 MP3와 작업용 사본 분리

위 테스트와 기존 전체 완주 기준을 모두 통과해야 단계 11까지 완료로 보고합니다.
