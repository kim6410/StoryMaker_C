# StoryMaker_C 단계 9 이후 UI·UX 및 관리자 편의성 고도화 상세 작업지시

작성일: 2026-07-29

작업 루트: `F:\StoryMaker_C`

적용 시점: 단계 9(WASM·WebGPU·WebCodecs 로컬 가속 및 서버 폴백) 완료 직후

참고 대상:

- Dell V1 기반 Beta의 실제 제작 화면
- Dell V1·Beta의 보관함, 마이페이지, 회원관리, 구독관리, 관리자 프롬프트 편집 화면
- StoryMaker_C 단계 0~9까지 구현된 실제 기능과 DB 구조
- StoryMaker_C 단계 6B의 SNS 8채널 결과·영상원고 저장 구조

이 문서는 단순한 디자인 참고안이 아니다.

단계 9 완료 직후 Claude Code가 바로 구현에 들어갈 수 있도록 화면 구조, 사용자 흐름, 관리자 기능, 상태 표시, 모바일 대응, 검증 기준까지 정의한 실행용 작업지시다.

기존 Dell V1·Beta의 코드를 복사하지 않는다.

Dell V1·Beta에서 사용자가 직접 다듬어온 화면 구성과 사용 흐름은 요구사항으로만 해석하고, StoryMaker_C 구조에 맞게 새로 구현한다.

---

## 1. 작업 목적

StoryMaker_C의 기능 엔진이 단계 9까지 완성되면 다음 문제를 해결한다.

첫째, 기능은 동작하지만 사용자가 제작 순서를 이해하기 어려운 문제를 해결한다.

둘째, 콘텐츠 생성·TTS·SRT·MP4·썸네일·보관함으로 이어지는 긴 작업 흐름을 한 화면에서 명확히 보여준다.

셋째, 일반 사용자는 최소한의 조작만으로 결과물을 만들게 하고, 관리자는 사용자·작업·오류·사용량·프롬프트·미디어 상태를 한 화면에서 파악하게 한다.

넷째, Dell V1·Beta에서 반복적으로 다듬은 버튼 위치, 단계 순서, 복사 기능, 모바일 레이아웃, 보관함 상세보기, 관리자 프롬프트 편집 경험을 StoryMaker_C에 더 정돈된 구조로 반영한다.

다섯째, 이후 기능 추가 시 화면이 다시 복잡해지지 않도록 공통 UI 규칙과 상태 체계를 확정한다.

## 2. 최우선 UX 원칙

### 2.1 사용자는 기술 용어를 몰라도 된다

일반 사용자 화면에서는 다음 용어를 직접 노출하지 않는다.

- JSON
- API Provider
- WebGPU
- WebCodecs
- WASM
- ffmpeg
- migration
- worker
- queue
- codec
- repository

사용자에게는 다음처럼 표현한다.

- AI 원고 만들기
- 음성 만들기
- 자막 만들기
- 영상 만들기
- 썸네일 선택하기
- 결과 저장하기

기술 상세는 관리자 화면과 진단 화면에만 표시한다.

### 2.2 한 화면에서 한 가지 핵심 행동만 강조한다

각 단계마다 가장 중요한 버튼은 하나만 강하게 표시한다.

예:

- 원고 생성 전: `콘텐츠 자동생성`
- 원고 생성 후: `음성 만들기`
- 음성 완료 후: `영상 만들기`
- 영상 완료 후: `대표 썸네일 선택`
- 전체 완료 후: `보관함에서 확인`

보조 버튼은 시각적으로 한 단계 낮춘다.

### 2.3 사용자는 현재 위치와 다음 행동을 항상 알아야 한다

모든 제작 화면 상단에는 다음을 표시한다.

- 현재 프로젝트명
- 업체명
- 현재 단계
- 완료한 단계 수
- 다음 해야 할 행동
- 마지막 저장 시각

### 2.4 자동 진행은 하되 통제권은 사용자에게 남긴다

자동 실행되는 단계는 진행 상태와 취소 가능 여부를 명확히 표시한다.

자동 진행 중에도 사용자가 다음을 확인할 수 있어야 한다.

- 현재 처리 중인 단계
- 예상 남은 시간 범위
- 이미 완료된 결과
- 실패 시 재시도 가능한 위치
- 서버 렌더와 로컬 렌더 선택 상태

### 2.5 실패 메시지는 원인보다 행동을 먼저 알려준다

나쁜 예:

`TTS_PROVIDER_TIMEOUT`

좋은 예:

`음성 생성이 지연되고 있습니다. 잠시 후 실패한 문장부터 다시 시도할 수 있습니다.`

관리자 상세보기에서는 내부 오류코드를 함께 표시한다.

### 3.1 일반 사용자 메뉴

PC 왼쪽 사이드 메뉴 또는 상단 메뉴는 다음 순서를 유지한다.

3. 내 보관함
4. 업체 정보
5. 구독·사용량
6. 도움말

### 3.2 관리자 메뉴

관리자 전용 메뉴는 다음 순서로 구성한다.

1. 관리자 대시보드
2. 회원관리
3. 작업관리
4. 콘텐츠·미디어 점검
5. 사용량·구독관리
6. 프롬프트 관리
7. AI Provider 관리
8. TTS·렌더 상태
9. 저장소·용량관리
10. 감사로그
11. 시스템 진단

### 3.3 모바일 메뉴

모바일에서는 하단 고정 메뉴를 기본으로 한다.

- 홈
- 제작
- 보관함
- 마이

관리자 모바일 화면에서는 하단 메뉴를 사용하지 않고, 상단 햄버거 메뉴와 검색 중심 구조를 사용한다.

## 4. 공통 디자인 시스템

### 4.1 화면 폭

PC 최대 콘텐츠 폭은 1440px 전후로 제한한다.

제작 화면은 좌우 여백을 줄이고 작업 영역을 넓게 사용한다.

관리자 테이블 화면은 최대 폭 제한을 완화한다.

모바일은 가로 스크롤이 발생하지 않아야 한다.

### 4.2 카드 규칙

카드를 과도하게 중첩하지 않는다.

한 화면에서 카드 테두리는 최대 2단계까지만 허용한다.

카드 기본 구성:

- 제목
- 짧은 설명
- 상태 배지
- 핵심 내용
- 하단 행동 버튼

### 4.3 버튼 체계

버튼은 네 종류로 통일한다.

- Primary: 현재 단계의 핵심 행동
- Secondary: 보조 행동
- Ghost: 복사, 미리보기, 상세보기
- Danger: 삭제, 강제종료, 사용정지

삭제 버튼은 일반 버튼과 붙이지 않는다.

삭제 전에는 대상과 영향을 명확히 설명하는 확인창을 표시한다.

### 4.4 상태 색상

상태 색상을 화면 전체에서 통일한다.

- 대기: 회색
- 진행 중: 파랑
- 완료: 초록
- 경고: 주황
- 실패: 빨강
- 사용자 수정됨: 보라
- 보존 잠금: 진한 남색

색상만으로 상태를 구분하지 않고 텍스트와 아이콘을 함께 사용한다.

### 4.5 문장과 간격

모바일에서 한 문단은 3~4줄을 넘기지 않는다.

버튼 문구는 명사보다 행동형으로 쓴다.

예:

- `생성`보다 `콘텐츠 자동생성`
- `저장`보다 `업체 정보 저장`
- `이동`보다 `보관함에서 확인`

## 5. 사용자 대시보드 고도화

### 5.1 대시보드 첫 화면

상단에는 환영 문구보다 현재 사용 상태를 먼저 보여준다.

필수 카드:

- 이번 달 사용량
- 남은 제작 횟수
- 보관함 사용량
- 최근 작업 상태
- 구독 만료일

가장 넓은 영역에는 `새 콘텐츠 만들기` 버튼을 둔다.

### 5.2 최근 작업

최근 작업 5개를 표시한다.

각 항목에 다음을 표시한다.

- 업체명
- 콘텐츠 제목
- 제작일
- 현재 단계
- 완료율
- 대표 썸네일
- 이어서 작업 버튼

실패 작업은 빨간색만 표시하지 말고 `실패한 단계부터 다시 시작` 버튼을 제공한다.

### 5.3 처음 사용하는 사용자

업체 정보가 없으면 제작 버튼을 바로 누르게 하지 않는다.

다음 순서의 온보딩을 표시한다.

1. 업체 정보 등록
2. 첫 콘텐츠 만들기
3. 결과 복사 또는 다운로드

진행률은 3단계로 단순하게 표시한다.

## 6. 콘텐츠 제작 화면 고도화

### 6.1 전체 레이아웃

PC 화면은 다음 3영역으로 구성한다.

왼쪽:

- 제작 단계 내비게이션

가운데:

- 현재 단계 입력·결과 영역

오른쪽:

- 업체 정보 요약
- 사용량
- 작업 상태
- 최근 자동저장 시각

모바일에서는 오른쪽 정보 영역을 접이식 상단 요약으로 변경한다.

### 6.2 제작 단계 표시

Dell Beta에서 다듬은 1~6단계 흐름을 StoryMaker_C 기능에 맞게 다음처럼 확장한다.

1. 기본 내용 입력
2. 이미지·영상 선택
3. AI 원고 생성
4. SNS 8채널 결과 확인
5. 음성·자막 생성
6. 영상 만들기
7. 대표 썸네일 선택
8. 저장·다운로드

단계 번호와 이름을 항상 표시한다.

완료된 단계는 체크 표시한다.

현재 단계는 강하게 강조한다.

아직 갈 수 없는 단계는 잠금 처리하되 이유를 표시한다.

### 6.3 기본 내용 입력

업체 정보는 마이페이지 DB에서 자동 불러온다.

사용자가 매번 입력하지 않도록 한다.

표시 항목:

- 업체명
- 업종
- 지역
- 주요 서비스
- 핵심 장점
- 전화번호
- 요청사항
- 금지 표현

현재 작업에서만 바꿀 수 있는 임시 수정 버튼을 제공한다.

원본 업체 정보 변경과 이번 작업만 변경을 명확히 구분한다.

### 6.4 이미지·영상 선택

파일 업로드 영역은 클릭과 드래그 앤드 드롭을 모두 지원한다.

업로드 후 다음 정보를 표시한다.

- 미리보기
- 파일명
- 파일 유형
- 해상도
- 길이
- 용량
- 사용 여부
- 순서 변경

여러 파일을 선택하면 드래그로 순서를 바꿀 수 있어야 한다.

깨진 파일이나 지원하지 않는 형식은 업로드 직후 알려준다.

### 6.5 AI 원고 생성

Dell Beta에서 사용자가 다듬은 핵심 흐름을 유지한다.

- `콘텐츠 자동생성` 버튼은 눈에 잘 띄는 단일 Primary 버튼
- 버튼 바로 아래 진행 상태 표시
- 별도 하단 카드로 진행 상태를 멀리 분리하지 않음
- 생성 중에는 화려하되 과하지 않은 단계 애니메이션 표시
- 8채널 결과가 모두 저장되면 자동으로 결과 영역으로 스크롤

진행 메시지 예:

- 업체 정보를 확인하고 있습니다
- 채널별 문체를 구성하고 있습니다
- SNS 8채널 콘텐츠를 작성하고 있습니다
- 영상 원고를 정리하고 있습니다
- 결과를 저장하고 있습니다

### 6.6 SNS 8채널 결과 화면

채널 탭은 다음 순서를 기본으로 한다.

1. 네이버 블로그
2. 인스타그램
3. 페이스북
4. 당근마켓
5. 네이버 플레이스
6. 구글 비즈니스 프로필
7. 카카오채널
8. 숏폼 영상 원고

각 채널 카드에는 다음 기능을 제공한다.

- 내용 보기
- 복사
- 수정
- 원본 복원
- 이 채널만 다시 생성
- 글자 수
- 생성 시각
- 수정 상태

복사 버튼은 제목 바로 옆에 둔다.

사용자가 가장 많이 쓰는 행동이므로 작게 숨기지 않는다.

네이버 블로그 복사는 HTML 서식을 유지하는 방식과 일반 텍스트 복사를 분리한다.

복사 성공 시 버튼 문구가 잠시 `복사 완료`로 바뀐다.

### 6.7 숏폼 영상 원고 편집

영상 원고는 일반 SNS 글과 분리한다.

다음 3개 영역으로 표시한다.

- 전체 내레이션 원고
- 장면별 문장
- 예상 영상 길이

장면별 문장은 순서 변경이 가능해야 한다.

문장 삭제·추가 후 TTS 재생성 범위를 안내한다.

## 7. TTS·SRT 사용자 화면

### 7.1 음성 설정

일반 사용자에게는 복잡한 모델명을 보여주지 않는다.

선택 항목:

- 여성 음성
- 남성 음성
- 밝은 톤
- 차분한 톤
- 속도

고급 설정은 접어서 제공한다.

### 7.2 문장별 상태

문장별 TTS 결과를 리스트로 보여준다.

각 행:

- 문장 번호
- 문장 내용
- 음성 길이
- 재생 버튼
- 상태
- 이 문장만 다시 만들기

전체 실패처럼 보이지 않도록 문장별 부분 재시도를 강조한다.

### 7.3 SRT 미리보기

SRT 원문 파일을 그대로 보여주지 않는다.

시간대별 자막 미리보기 형태로 표시한다.

- 시작 시각
- 종료 시각
- 자막 문장
- 줄바꿈 미리보기

관리자 또는 고급 사용자만 원본 SRT 보기 기능을 사용할 수 있게 한다.

## 8. 영상 제작 화면

### 8.1 렌더 방식 선택

사용자에게 기술 용어 대신 다음 두 선택지를 제공한다.

- 내 PC에서 빠르게 만들기
- 서버에서 안정적으로 만들기

각 선택지 아래 설명:

내 PC:

- PC 성능을 사용
- 탭을 닫으면 중단될 수 있음
- 지원되는 환경에서 더 빠를 수 있음

서버:

- 시간이 조금 더 걸릴 수 있음
- 화면을 닫아도 계속 진행 가능
- 저사양 PC에 권장

### 8.2 진행률

단순한 전체 퍼센트만 보여주지 않는다.

단계별 진행률을 표시한다.

- 미디어 준비
- 음성·음악 결합
- 장면 구성
- 자막 적용
- 영상 인코딩
- 최종 검증

### 8.3 미리보기

영상 완료 후 자동재생은 기본적으로 끈다.

사용자가 재생 버튼을 눌러 확인하게 한다.

표시 정보:

- 영상 길이
- 해상도
- 파일 크기
- 생성 방식
- 음성 포함
- 배경음악 포함
- 자막 포함

### 8.4 실패 복구

실패 시 `처음부터 다시 만들기`만 제공하지 않는다.

오류 단계에 따라 다음 버튼을 제공한다.

- 영상 단계만 다시 시도
- 서버 방식으로 전환
- 내 PC 방식으로 다시 시도
- 문제 파일 교체

### 8.5 전화번호 TTS 정규화 규칙

전화번호는 숫자 전체를 일반 수량처럼 읽지 않는다.

하이픈 또는 공백으로 구분된 전화번호는 각 묶음을 한 자리씩 읽는다.

대표 예시:

- 입력: `010-8284-5584`
- TTS 읽기: `공일공, 팔이팔사, 오오팔사`

쉼표 위치에는 짧은 자연스러운 호흡을 넣는다.

권장 쉼 시간:

- 번호 묶음 사이: 0.25초~0.4초
- 전화번호 앞뒤: 0.15초~0.25초

다음 표기들도 같은 결과로 정규화한다.

- `010 8284 5584`
- `010.8284.5584`
- `01082845584`
- `전화 010-8284-5584`
- `문의전화: 010-8284-5584`

숫자 읽기 표준:

- 0: 공
- 1: 일
- 2: 이
- 3: 삼
- 4: 사
- 5: 오
- 6: 육
- 7: 칠
- 8: 팔
- 9: 구

전화번호를 `십억`, `팔천이백팔십사`처럼 수량 단위로 읽는 것을 금지한다.

지역번호, 대표번호, 고객센터 번호도 동일 원칙을 적용한다.

예:

- `052-123-4567` → `공오이, 일이삼, 사오육칠`
- `1588-1234` → `일오팔팔, 일이삼사`
- `02-1234-5678` → `공이, 일이삼사, 오육칠팔`

원본 표시용 문자열과 TTS 정규화 문자열을 분리 저장한다.

화면에는 원본 전화번호를 보여주고, 관리자 또는 고급 사용자에게만 `TTS 읽기 미리보기`를 제공한다.

완료 기준:

- `010-8284-5584`가 정확히 `공일공, 팔이팔사, 오오팔사`로 생성됨
- 전화번호 원문은 자막과 화면 표시에서 유지됨
- TTS용 문자열만 변환됨
- 전화번호가 포함되지 않은 일반 숫자에는 전화번호 규칙을 잘못 적용하지 않음
- 단위 테스트에 하이픈·공백·점·무구분 번호를 모두 포함

### 8.6 MP4 시작·종료 오디오 타임라인

최종 MP4의 시작과 끝은 음성·배경음악이 갑자기 튀지 않도록 고정 타임라인 규칙을 적용한다.

시작 규칙:

1. 영상은 0초부터 시작한다.
2. 배경음악은 0초부터 무음에 가까운 상태로 시작한다.
3. 배경음악은 1.5초 동안 자연스럽게 페이드인한다.
4. TTS는 배경음악 페이드인 1.5초가 끝난 직후 시작한다.
5. 첫 장면은 TTS가 시작되기 전에도 정지 화면처럼 보이지 않도록 약한 움직임을 적용할 수 있다.

기본 타임라인:

- `00:00.000` 영상 시작
- `00:00.000 ~ 00:01.500` 배경음악 페이드인
- `00:01.500` TTS 시작

종료 규칙:

1. 마지막 TTS 문장이 완전히 끝날 때까지 배경음악을 낮은 음량으로 유지한다.
2. TTS 종료 직후 배경음악 페이드아웃을 시작한다.
3. 배경음악은 2초 동안 자연스럽게 페이드아웃한다.
4. 페이드아웃이 끝난 뒤 영상이 종료된다.
5. 마지막 화면은 최소 2초간 유지되므로 상호와 전화번호를 읽고 확인할 시간이 확보돼야 한다.

기본 종료 타임라인:

- `TTS_END` 마지막 음성 종료
- `TTS_END ~ TTS_END+2.000` 배경음악 페이드아웃
- `TTS_END+2.000` 영상 종료

최종 영상 길이 계산:

`1.5초 시작 여유 + 전체 TTS 길이 + 2초 종료 여유`

장면과 자막의 전체 타임라인도 이 시작 지연을 반영한다.

첫 자막 시작시각은 원칙적으로 1.5초 이후다.

마지막 자막은 마지막 TTS 종료시각을 넘기지 않는다.

배경음악 페이드아웃 구간에는 마지막 업체 정보 화면을 유지한다.

완료 기준:

- 시작 1.5초 동안 TTS가 재생되지 않음
- 배경음악이 갑자기 최대 음량으로 시작하지 않음
- TTS 종료 직후 영상이 잘리지 않음
- TTS 종료 후 정확히 약 2초간 배경음악이 줄어든 뒤 영상 종료
- 최종 MP4 길이와 계산 타임라인 오차 100ms 이내 목표
- ffprobe로 오디오·영상 길이 검증
- 음성 끝부분 잘림 0건

### 8.7 배경음악과 TTS 음량 관계

배경음악은 TTS보다 항상 뒤에 있어야 한다.

기본 원칙:

- 음성 명료도가 최우선
- TTS가 말하는 동안 배경음악 자동 감쇠 또는 Ducking 적용
- 문장 사이 짧은 공백에는 음악이 과도하게 출렁이지 않도록 완만한 복귀 적용
- TTS가 끝난 뒤 2초 페이드아웃 구간에서는 음악이 자연스럽게 조금 살아났다 사라질 수 있음

권장 기본값은 실제 청취 테스트로 확정하되 코드에 여러 곳으로 흩어 쓰지 않는다.

관리자 렌더 설정 또는 공통 미디어 설정에서 관리한다.

사용자 화면에서는 복잡한 dB 수치보다 다음 3단계만 제공한다.

- 잔잔하게
- 보통
- 조금 크게

`보통`을 기본값으로 한다.

TTS가 묻히는 설정은 저장 또는 렌더 전에 경고한다.

### 8.8 자막·상호·전화번호 창의적 배치 원칙

자막, 상호, 전화번호의 정확한 좌표를 하나의 고정값으로 강제하지 않는다.

Claude Code는 장면 구성과 화면 안전영역을 분석해 자연스럽고 읽기 쉬운 위치를 창의적으로 선택할 수 있다.

다만 창의성은 다음 강제 조건 안에서만 허용한다.

자막:

- 기본은 화면 하단 안전영역
- 인물 얼굴, 제품 핵심부, 간판, 작업 장면의 핵심 피사체를 가리지 않음
- 한 줄 또는 최대 두 줄
- 모바일 9:16 화면에서 즉시 읽을 수 있는 크기
- 흰 글자와 충분한 검은 외곽선 또는 반투명 배경 사용
- 배경 밝기에 따라 자동 대비 보정 가능
- 화면 가장자리와 충분한 여백 유지

상호:

- 영상 전체에서 계속 표시하거나, 장면별로 최소한만 노출할 수 있음
- 상단 좌측, 상단 중앙, 하단 별도 띠 등 장면에 맞게 선택 가능
- 자막과 겹치지 않음
- 업체명은 전화번호보다 시각적 우선순위를 높게 둠
- 마지막 2초에는 반드시 명확하게 표시

전화번호:

- 상호 가까이에 배치하되 한 덩어리로 답답하게 붙이지 않음
- 원문 표기 `010-8284-5584` 유지
- 마지막 2초에는 반드시 표시
- 자막과 겹치지 않음
- 클릭 가능한 UI가 아닌 영상 안의 텍스트이므로 숫자 가독성을 최우선으로 함

배치 후보:

- 상호 상단 좌측 + 전화번호 상단 우측
- 상호 상단 중앙 + 전화번호 하단 중앙
- 상호와 전화번호를 하단 정보 띠 안에서 좌우 분리
- 마지막 엔딩 카드에서 상호 중앙, 전화번호 그 아래

금지:

- 자막·상호·전화번호 세 요소를 모두 화면 하단 한곳에 겹쳐 배치
- 전화번호가 자막에 가려지는 구성
- 배경과 같은 색으로 숫자가 사라지는 구성
- 장면마다 위치가 심하게 바뀌어 시선이 흔들리는 구성
- 화면 가장자리 3% 이내에 텍스트 배치
- 상호나 전화번호가 잘리거나 영상 밖으로 나가는 구성

관리자 미리보기에서는 안전영역 가이드와 실제 배치 박스를 켜고 끌 수 있게 한다.

완료 기준:

- 8개 이상의 서로 다른 밝기·구도 샘플에서 텍스트 가독성 확인
- 9:16 모바일 미리보기에서 잘림 없음
- 얼굴·제품·작업 핵심부 가림 최소화
- 마지막 2초 상호·전화번호 노출 확인
- 자막과 업체 정보 충돌 0건

### 8.9 줌인·줌아웃과 카메라 움직임 기준

MP4의 줌인·줌아웃은 화면을 풍성하게 만드는 보조 수단이며, 사용자가 어지럽게 느껴서는 안 된다.

기본 원칙:

- 한 장면에서 한 방향의 움직임만 사용
- 짧은 시간에 줌인과 줌아웃을 반복하지 않음
- 장면마다 움직임 방향을 무조건 바꾸지 않음
- 피사체 중심을 유지
- 사람 얼굴이나 제품을 화면 밖으로 밀어내지 않음
- 빠른 패닝·급격한 확대 금지

권장 줌 범위:

- 시작 배율: 1.00~1.04
- 종료 배율: 1.06~1.14
- 한 장면 내 총 확대 변화는 기본 12% 이내
- 세로형 저해상도 이미지에서는 8% 이내 우선

권장 움직임:

- 천천히 줌인
- 천천히 줌아웃
- 아주 약한 좌우 이동
- 아주 약한 상하 이동
- 정지 화면

한 영상 안에서 정지 장면도 섞어야 한다.

모든 장면을 움직이게 만들지 않는다.

권장 리듬:

- 움직임 장면 2개 뒤 정지 또는 매우 약한 장면 1개
- 같은 줌 효과 3회 이상 연속 사용 금지
- 장면 길이가 3초 미만이면 강한 줌 사용 금지

사용자가 업로드한 영상 소스에는 추가 줌을 기본적으로 적용하지 않는다.

이미 카메라 움직임이 있는 영상 위에 인위적인 줌을 겹치지 않는다.

완료 기준:

- 전체 영상을 두 번 연속 시청해도 어지러움이 없음
- 피사체가 프레임 밖으로 잘리지 않음
- 갑작스러운 배율 변화 없음
- 장면 시작·끝에서 위치 점프 없음
- 동일 효과의 기계적 반복이 눈에 띄지 않음

### 8.10 화면 전환 효과 2.5초 기준

장면 전환은 기본적으로 2.5초 동안 자연스럽게 이어지도록 한다.

기본 전환 시간:

`2.5초`

우선 전환 효과:

- 크로스 디졸브
- 부드러운 페이드
- 아주 약한 슬라이드 디졸브
- 밝기 변화가 적은 블렌드

기본값은 크로스 디졸브로 한다.

전환 시간 동안 이전 장면과 다음 장면이 자연스럽게 겹친다.

전환이 음성 문장 중간의 의미를 방해하지 않도록 가능하면 문장 경계 또는 장면 문장 경계에 맞춘다.

전환 중 자막은 다음 원칙을 따른다.

- 이전 문장 자막은 음성 종료와 함께 사라짐
- 다음 문장 자막은 다음 TTS 시작에 맞춰 표시
- 전환 화면 때문에 자막이 두 겹으로 보이지 않음
- 상호·전화번호 위치는 전환 중 갑자기 튀지 않도록 보간 또는 고정

2.5초 전환을 그대로 적용하기 어려운 짧은 장면은 전환 시간을 자동 축소할 수 있다.

단, 장면 길이의 절반을 넘는 전환은 금지한다.

권장 자동 규칙:

- 장면 길이 6초 이상: 2.5초
- 장면 길이 4~6초: 1.5~2.2초
- 장면 길이 3~4초: 1.0~1.5초
- 장면 길이 3초 미만: 0.5~1.0초 또는 컷 유지

금지 효과:

- 번쩍임
- 과도한 회전
- 화면 뒤집기
- 빠른 확대 전환
- 과도한 글리치
- 매 장면 다른 효과
- 시선을 강제로 흔드는 3D 전환

영상 전체에서 전환 프리셋은 최대 2종만 사용한다.

관리자가 별도 설정하지 않으면 한 영상은 동일한 전환 계열로 통일한다.

완료 기준:

- 기본 장면 전환이 약 2.5초로 자연스럽게 이어짐
- 짧은 장면에서 전환이 장면 자체를 삼키지 않음
- 검은 프레임이나 빈 프레임 없음
- 장면 경계에서 음성·자막 싱크 유지
- 상호·전화번호가 전환 중 튀지 않음
- 동일 영상을 모바일에서 시청했을 때 피로감이 없음

### 8.11 엔딩 화면 구성

마지막 TTS가 끝나면 마지막 장면을 유지한 채 배경음악이 2초 동안 페이드아웃한다.

이 2초는 단순한 빈 여백이 아니라 업체 정보를 각인시키는 엔딩 구간으로 사용한다.

필수 표시:

- 업체명
- 전화번호

선택 표시:

- 핵심 서비스 한 줄
- 지역
- 짧은 행동 유도 문구

예:

- `울산 집수리·설비 상담`
- `빠른 방문 상담이 필요할 때 연락주세요`

엔딩 화면은 본문 자막을 표시하지 않아도 된다.

상호와 전화번호를 가장 명확하게 읽을 수 있도록 배경 어둡기 또는 블러를 약하게 적용할 수 있다.

전화번호는 반드시 원문 `010-8284-5584`로 표시한다.

### 8.12 사용자·관리자 미리보기 보강

영상 렌더 전 사용자에게 다음 미리보기를 제공한다.

- 첫 5초 오디오 미리듣기
- 마지막 5초 엔딩 미리보기
- 자막 위치 미리보기
- 상호·전화번호 위치 미리보기
- 줌 효과 강도 미리보기
- 전환 효과 미리보기

사용자 설정은 단순하게 유지한다.

- 움직임: 없음 / 잔잔하게 / 조금 역동적으로
- 전환: 자연스럽게 / 빠르게
- 업체정보 위치: 자동 / 상단 / 하단

기본값:

- 움직임: 잔잔하게
- 전환: 자연스럽게
- 업체정보 위치: 자동

관리자 화면에는 실제 내부값과 검증 결과를 추가 표시한다.

- 시작 페이드인 시간
- TTS 시작 오프셋
- 종료 페이드아웃 시간
- 장면별 전환 시간
- 장면별 줌 시작·종료 배율
- 자막 좌표
- 상호 좌표
- 전화번호 좌표
- 안전영역 충돌 여부

### 8.13 MP4 종합 완료 기준

다음 조건을 모두 통과해야 영상 제작 완료로 처리한다.

1. 배경음악이 1.5초 동안 페이드인한 뒤 TTS가 시작된다.
2. 마지막 TTS가 끝난 뒤 배경음악이 2초 동안 페이드아웃하고 영상이 종료된다.
3. 전화번호 `010-8284-5584`의 TTS 읽기가 `공일공, 팔이팔사, 오오팔사`로 확인된다.
4. 자막은 TTS 실제 발화 시각과 일치한다.
5. 자막·상호·전화번호가 서로 겹치지 않는다.
6. 상호와 전화번호는 마지막 2초 동안 명확히 표시된다.
7. 줌인·줌아웃이 느리고 안정적이며 어지럽지 않다.
8. 화면 전환은 기본 2.5초의 자연스러운 전환을 사용한다.
9. 짧은 장면에서는 전환 시간이 자동 축소된다.
10. 검은 화면, 빈 프레임, 음성 잘림, 음악 급정지 현상이 없다.
11. H.264·AAC·30fps·yuv420p·faststart 조건을 검증한다.
12. PC 브라우저와 모바일 브라우저에서 실제 재생을 확인한다.
13. 일반 플레이어에서 실제 재생을 확인한다.
14. 서버 렌더와 로컬 렌더 결과가 같은 타임라인 규칙을 따른다.
15. 실패 시 MP4 단계만 다시 시도할 수 있다.

## 9. 썸네일 선택 화면

Dell Beta에서 다듬은 흐름을 그대로 요구사항으로 유지한다.

- 9:16 세로형 8종을 우선 표시
- 미리보기 8개는 브라우저에서 생성 가능
- 선택 전 서버 저장 0개
- 사용자가 선택한 대표 썸네일 1개만 저장
- 재선택 시 기존 대표 썸네일 교체
- 보관함에는 대표 썸네일 1개만 표시

- 확대 보기
- 선택
- 선택 강조
- 저장 확인

선택 후 바로 저장하지 않고 다음 확인창을 표시한다.

`이 썸네일을 대표 이미지로 저장할까요?`

저장 성공 후 실제 파일 크기와 저장 완료 상태를 표시한다.

기존 보관함 결과가 자동 변경되지 않는다는 점을 명확히 한다.

## 31. WASM·WebGPU·WebCodecs 로컬 가속과 서버 폴백 실전 성공기 및 적용 명세

이 장은 단계 9의 핵심 엔진을 단순히 구현하는 수준을 넘어, Dell V1·Beta에서 실제로 성공과 실패를 반복하며 얻은 운영 노하우를 StoryMaker_C에 옮기기 위한 실행 기준이다.

목표는 최신 PC에서만 빠른 데모를 만드는 것이 아니다.

고성능 PC에서는 로컬 자원을 적극 활용하고, 저사양 PC나 브라우저 제약 환경에서는 사용자가 실패를 경험하기 전에 서버 방식으로 자연스럽게 전환하며, 어느 경로를 사용하더라도 결과물 계약과 보관함 저장 방식은 동일하게 유지하는 것이다.

### 31.1 Dell V1·Beta에서 실제로 확인한 성공 흐름

Dell V1·Beta에서는 다음 흐름을 실제로 완주했다.

1. AI 원고 생성 완료
2. TTS·MP3 생성 완료
3. SRT 생성 완료
4. 브라우저에서 이미지·음성·자막을 불러옴
5. WebGPU 또는 WASM 경로로 장면을 준비
6. WebCodecs 계열 브라우저 렌더러로 MP4 생성
7. 생성 Blob을 서버에 업로드
8. DB·result.json·보관함에 최종 MP4 연결
9. 대표 썸네일 생성 및 선택 저장
10. 전체 결과물 다운로드

실전 성공에서 가장 중요한 점은 단순히 브라우저에서 MP4 Blob이 생성됐다는 사실이 아니다.

브라우저에서 생성한 결과가 서버의 현재 작업 ID와 정확히 연결되고, 서버가 해당 파일을 정상 결과로 인정하며, 보관함에서 다시 재생·다운로드할 수 있어야 전체 성공으로 판정했다.

Dell V1·Beta에서는 일반 PC와 저사양 PC에서 실제 사용 테스트를 수행했고, 최신 노트북에서는 비교적 빠르게 완료됐으며, 오래된 인텔 3세대·RAM 4GB 수준 PC에서도 조건에 따라 전체 흐름을 완주한 사례가 있었다.

이 경험으로 확인한 핵심은 다음과 같다.

- 사용자 PC 자원을 활용하면 서버의 CPU·GPU 부담을 크게 줄일 수 있다.
- 브라우저 렌더는 무료 또는 낮은 서버 비용 구조에 유리하다.
- PC 성능 차이가 크므로 로컬 렌더만 강제하면 안 된다.
- 브라우저 기능 지원 여부보다 실제 렌더 성공 여부가 더 중요하다.
- 최종 성공은 화면 표시가 아니라 서버 저장·DB 연결·재생 검증까지 포함해야 한다.

### 31.2 WebGPU·WASM의 역할 분리

StoryMaker_C에서는 WebGPU와 WASM을 서로 경쟁하는 단일 선택지로 취급하지 않는다.

각 역할을 다음처럼 분리한다.

#### WebGPU 우선 경로

WebGPU가 실제로 사용 가능하고 안정적인 환경에서는 다음 작업에 우선 활용한다.

- 이미지 스케일링
- 장면 합성
- 색상·밝기 조정
- 줌인·줌아웃 프레임 계산
- 전환 효과 프레임 계산
- 일부 필터와 오버레이 처리
- 가능한 경우 TTS 추론 가속

WebGPU 사용 가능 여부는 단순히 `navigator.gpu` 존재만으로 판단하지 않는다.

반드시 Adapter 요청, Device 생성, 최소 연산 또는 테스트 프레임 처리까지 성공해야 `webgpu_ready`로 판정한다.

#### WASM 안전 경로

WebGPU가 없거나 초기화에 실패했을 때는 WASM 또는 일반 Canvas 기반 경로를 유지한다.

WASM 경로는 다음 역할을 맡는다.

- CPU 기반 이미지 처리
- 오디오 후처리
- 형식 변환
- 간단한 타임라인 계산
- WebGPU 미지원 브라우저의 대체 처리

Dell Beta의 경험상 WebGPU가 실패해도 WASM 경로를 유지하면 일부 장비에서 작업 전체를 포기하지 않고 다음 단계로 진행할 수 있었다.

다만 WASM은 저사양 PC에서 처리 시간이 길어질 수 있으므로 무제한 대기시키지 않는다.

### 31.3 WebCodecs의 실제 사용 원칙

WebCodecs는 브라우저 안에서 프레임을 인코딩하기 위한 핵심 수단이지만, 브라우저마다 지원 코덱과 동작이 다를 수 있다.

다음 순서로 검사한다.

1. `VideoEncoder` 존재 여부
2. 대상 코덱의 `isConfigSupported()` 결과
3. 실제 소형 프레임 1~3개 시험 인코딩
4. 출력 Chunk 수신 여부
5. MP4 Muxer 초기화 가능 여부
6. AudioEncoder 또는 대체 오디오 경로 확인
7. 최종 컨테이너 생성 가능 여부

지원 여부 API가 성공해도 실제 인코딩이 실패할 수 있으므로 소형 시험 인코딩을 생략하지 않는다.

기본 출력 코덱은 범용 재생성을 우선한다.

- 영상: H.264 계열 우선
- 오디오: AAC 계열 우선
- 컨테이너: MP4

브라우저에서 H.264 인코딩을 지원하지 않으면 다음 순서로 처리한다.

1. 가능한 대체 브라우저 코덱으로 임시 렌더
2. 서버에서 H.264 MP4로 재인코딩
3. 또는 즉시 서버 렌더로 전환

사용자가 브라우저 코덱 차이를 직접 선택하게 하지 않는다.

### 31.4 Worker 분리와 UI 멈춤 방지

Dell Beta에서는 무거운 TTS 또는 MP4 처리를 메인 UI 스레드에서 직접 실행하면 화면 멈춤, 버튼 무응답, 진행 표시 정지 문제가 발생할 수 있음을 확인했다.

StoryMaker_C에서는 다음을 원칙으로 한다.

- 프레임 생성과 인코딩은 Web Worker에서 실행
- 메인 스레드는 UI와 진행 상태 표시만 담당
- Worker와 메인 화면 간 메시지 계약을 명시
- 한 작업에 Worker 한 세션만 허용
- 작업 종료 후 Worker를 명시적으로 종료
- 페이지 이탈 시 Worker 정리
- 실패 후 재시도 시 이전 Worker 재사용 금지

Worker 메시지 예시:

- `renderer_ready`
- `media_loaded`
- `frame_progress`
- `encoding_progress`
- `muxing`
- `uploading`
- `completed`
- `failed`
- `cancelled`

진행률은 Worker 내부 실제 처리량을 기준으로 계산한다.

단순 시간 경과 기반 가짜 퍼센트는 금지한다.

### 31.5 초기 준비와 Warm-up 노하우

Dell Beta의 TTS·WebGPU 준비 과정에서는 첫 작업 시작 시 Worker와 ONNX 세션을 동시에 만들면서 초기 지연이 발생했다.

이를 줄이기 위해 실제 작업 ID가 만들어진 직후 백그라운드에서 준비 요청을 보냈고, TTS 시작 시 준비 Promise를 재사용했다.

StoryMaker_C에서도 다음을 적용한다.

1. 제작 화면 진입 직후 기능 탐지만 수행
2. 사용자가 영상 제작 단계에 가까워지면 Renderer Worker 준비
3. WebGPU Adapter·Device 준비
4. WASM 모듈 준비
5. Muxer 모듈 준비
6. 코덱 지원 시험
7. 짧은 Warm-up 프레임 실행
8. 결과를 세션 상태에 보관

사용자가 아직 이미지나 원고를 입력하지 않은 초기 화면에서 대형 모델과 모든 미디어 엔진을 한꺼번에 다운로드하지 않는다.

지연 로딩을 사용한다.

Warm-up 상태는 다음처럼 구분한다.

- `not_started`
- `loading`
- `ready`
- `unsupported`
- `failed`

Warm-up 실패가 전체 제작 실패로 이어지지 않게 하며, 서버 렌더 가능 여부를 즉시 함께 확인한다.

### 31.6 로컬 렌더 사전 적합성 검사

사용자가 `내 PC에서 빠르게 만들기`를 선택하기 전에 다음을 검사한다.

- 브라우저 종류와 버전
- WebGPU 실제 초기화 성공 여부
- WebCodecs 실제 시험 인코딩 성공 여부
- Worker 지원 여부
- OffscreenCanvas 지원 여부
- 사용 가능한 메모리 추정
- 입력 이미지 수와 총 해상도
- 입력 동영상 수와 총 길이
- 예상 프레임 수
- 예상 출력 해상도
- 이전 로컬 렌더 실패 이력

다음 조건에서는 서버 방식을 기본 권장한다.

- WebGPU와 WebCodecs 모두 실사용 불가
- 저사양 장치로 추정
- 메모리 부족 위험
- 입력 파일이 지나치게 많음
- 4K 또는 초고해상도 이미지가 다수 존재
- 긴 동영상이 다수 포함됨
- 동일 브라우저에서 직전 로컬 렌더 실패
- 모바일 브라우저에서 메모리 여유가 불명확

권장일 뿐 강제는 아니지만, 치명적 미지원 조건에서는 로컬 시작 버튼을 비활성화하고 이유를 설명한다.

### 31.7 입력 미디어 정규화

실전에서 브라우저 렌더 실패의 상당수는 렌더러 자체보다 입력 미디어의 해상도, 회전 정보, 색상 형식, 코덱 차이에서 발생할 수 있다.

렌더 전에 다음을 정규화한다.

#### 이미지

- EXIF 회전 반영
- 지나치게 큰 이미지는 목표 해상도에 맞게 축소
- 손상 이미지 사전 차단
- 투명 배경 처리 규칙 통일
- 색상 프로파일 차이 최소화
- 이미지 로딩 완료 후에만 프레임 생성

#### 업로드 동영상

- 길이 확인
- 코덱 확인
- 회전 메타데이터 확인
- 필요 시 서버 프록시 또는 정규화본 생성
- 브라우저 재생 불가 파일은 로컬 렌더 대상에서 제외
- 원본 영상에 과도한 추가 줌 금지

#### 오디오

- 샘플레이트 통일
- 채널 수 통일
- TTS와 배경음악 길이 확정
- 음량 정규화
- 페이드인·페이드아웃 적용
- 최종 혼합 WAV 또는 PCM 타임라인 확정

입력 정규화 완료 전에는 인코더를 시작하지 않는다.

### 31.8 메모리 관리

저사양 PC 성공의 핵심은 처리 속도보다 메모리를 폭발시키지 않는 것이다.

다음 원칙을 강제한다.

- 전체 영상을 모든 Raw Frame으로 메모리에 보관하지 않음
- 프레임 생성 즉시 Encoder에 전달
- 인코딩 완료 프레임은 즉시 `close()`
- `VideoFrame`, `ImageBitmap`, Canvas, Blob URL을 사용 후 해제
- 장면 단위로 이미지 리소스를 로드·해제
- 필요 이상으로 큰 OffscreenCanvas 생성 금지
- 중간 MP4 Blob을 여러 복사본으로 만들지 않음
- 다운로드용 Blob과 업로드용 Blob의 중복 생성을 최소화
- 취소·실패 시 모든 리소스 정리

고해상도 이미지는 원본 전체를 매 프레임 다시 디코딩하지 않는다.

장면 시작 시 목표 해상도용 Bitmap을 1회 준비하고 장면 종료 후 해제한다.

### 31.9 프레임 생성과 타임라인 정확성

렌더 타임라인은 실제 TTS·SRT 길이를 기준으로 생성한다.

장면별 시작·종료 시각은 DB 또는 확정된 manifest에 저장한다.

각 프레임의 timestamp는 누적 오차가 생기지 않도록 정수 마이크로초 또는 명확한 TimeBase를 사용한다.

다음 항목이 서로 일치해야 한다.

- TTS 실제 길이
- SRT 마지막 종료 시각
- 배경음악 타임라인
- 장면별 길이
- VideoFrame timestamp
- Audio timestamp
- 최종 MP4 duration

영상 전체 길이는 다음 규칙을 따른다.

`1.5초 시작 여유 + 전체 TTS 길이 + 2초 종료 여유`

전환 구간 2.5초는 두 장면의 길이에 중복 포함되는 오버랩 구간으로 처리하며, 전환 때문에 전체 영상 길이가 무조건 늘어나지 않게 한다.

장면 길이가 짧으면 전환 시간을 자동 축소한다.

### 31.10 렌더 잠금과 중복 실행 방지

Dell V1·Beta에서는 TTS, 브라우저 MP4 업로드, 서버 슬라이드쇼, DOM 감시 업로드가 중복 실행되면서 동일 작업이 2~3번 처리되는 문제가 있었다.

StoryMaker_C에서는 다음 잠금을 둔다.

- 작업 ID별 렌더 잠금
- 브라우저 세션별 렌더 잠금
- 업로드 중복 방지 키
- 서버 렌더 중복 요청 방지 키
- 완료 이벤트 중복 처리 방지

동일 작업에서 다음은 각각 1회만 허용한다.

- TTS 전체 생성
- SRT 확정
- 로컬 렌더 시작
- 서버 렌더 시작
- MP4 최종 업로드
- 보관함 완료 이벤트

브라우저가 새로고침됐을 때 기존 서버 작업이 진행 중이면 새 작업을 만들지 않고 현재 상태를 조회한다.

완료된 MP4가 이미 존재하고 해시·크기·duration 검증이 통과하면 재렌더하지 않는다.

### 31.11 로컬 렌더 시간 제한과 서버 폴백

Dell Beta에서는 저사양 PC에서 브라우저 MP4 인코딩이 120초를 초과하거나 오류로 종료될 때 자동으로 Dell 서버 렌더 API를 호출하도록 최소 폴백을 적용했다.

StoryMaker_C에서는 단순 고정 120초만 사용하지 않고 예상 작업량을 고려한 제한 시간을 사용한다.

예시:

- 준비 단계 제한
- 첫 프레임 생성 제한
- 프레임 진행 정체 제한
- 전체 렌더 제한
- 업로드 제한

폴백 조건:

- WebGPU 초기화 실패
- WebCodecs 시험 인코딩 실패
- Worker 비정상 종료
- 일정 시간 동안 프레임 진행 없음
- 메모리 부족 또는 브라우저 탭 종료 경고
- 인코더 오류
- Muxer 오류
- 로컬 렌더 제한 시간 초과
- 최종 MP4 검증 실패
- 업로드 반복 실패

폴백 순서:

1. 현재 로컬 렌더 상태를 실패 또는 중단으로 기록
2. Worker와 프레임 리소스 정리
3. 서버에 기존 TTS·SRT·미디어·타임라인 존재 여부 전달
4. 기존 정상 산출물 재사용
5. 서버는 MP4 단계만 렌더
6. 완료 후 작업 상태 재조회
7. 최종 MP4 URL을 동일한 결과 슬롯에 연결
8. 보관함 완료 이벤트 전송

폴백 시 AI 원고와 TTS를 처음부터 다시 생성하지 않는다.

### 31.12 서버 폴백에서 반드시 재사용할 산출물

Dell Beta 서버 폴백 과정에서 확인된 중요한 실패 원인은 서버가 이미 생성된 정확한 산출물을 무시하고 임의로 다시 만드는 것이었다.

StoryMaker_C에서는 다음을 절대 재생성하지 않는다.

- 검증 완료된 AI 원고
- 확정된 영상 원고
- 정상 생성된 TTS WAV 또는 MP3
- 실제 음성 길이에 맞춘 SRT
- 사용자가 선택한 이미지·동영상 순서
- 배경음악 선택
- 장면 타임라인
- 자막 설정
- 상호·전화번호 설정

특히 서버 폴백은 기존의 정확한 SRT를 덮어쓰지 않는다.

전체 음성 시간을 글자 수 비율로 다시 분배하는 방식은 금지한다.

배경음악이 포함된 최종 혼합 음원이 이미 있다면 이를 우선 사용한다.

### 31.13 로컬과 서버 결과 계약 통일

로컬 렌더와 서버 렌더는 구현 방식만 다르고 결과 계약은 같아야 한다.

공통 결과 메타데이터:

- 작업 ID
- 사용자 ID
- 렌더 방식
- 렌더러 버전
- 출력 코덱
- 해상도
- FPS
- 영상 길이
- 파일 크기
- SHA-256
- 음성 포함 여부
- 음악 포함 여부
- 자막 포함 여부
- 썸네일 연결 여부
- 생성 시작·종료 시각
- 재시도 횟수
- 폴백 원인

DB와 result manifest는 동일 필드를 사용한다.

보관함에서는 로컬 렌더인지 서버 렌더인지에 따라 기능이 달라지지 않아야 한다.

관리자 상세 화면에서만 렌더 방식을 표시한다.

### 31.14 최종 MP4 검증

Blob 생성 또는 파일 저장만으로 성공 처리하지 않는다.

다음 검증을 통과해야 한다.

- 파일 존재
- 파일 크기 0 초과
- MP4 컨테이너 파싱 가능
- 영상 스트림 존재
- 오디오 스트림 존재
- 목표 해상도 일치
- duration이 예상 범위와 일치
- 시작 1.5초 음악 페이드인 확인
- TTS 시작 위치 확인
- 마지막 TTS 이후 2초 음악 페이드아웃 확인
- SRT 또는 번인 자막 구간 확인
- 상호·전화번호 표시 확인
- 브라우저 재생 가능
- Range 요청 또는 스트리밍 재생 가능
- SHA-256 저장
- DB·manifest·실제 파일 경로 일치

최종 검증 실패 시 완료 상태로 바꾸지 않는다.

### 31.15 취소·새로고침·탭 종료 복구

로컬 렌더는 탭 상태에 영향을 받으므로 복구 UX가 중요하다.

#### 사용자가 취소할 때

- 현재 Worker에 취소 신호 전송
- 인코더 flush 또는 안전 종료
- 리소스 해제
- 임시 Blob 폐기
- 서버 상태를 `cancelled_local`로 기록
- 기존 TTS·SRT·미디어는 보존

#### 새로고침했을 때

- 작업 ID로 서버 상태 조회
- 로컬 렌더가 중단됐으면 재시작 또는 서버 전환 선택
- 서버 렌더가 진행 중이면 진행 상태 복원
- 이미 완료됐으면 결과 화면으로 이동

#### 탭 종료 경고

로컬 렌더 중에는 종료 경고를 표시한다.

서버 렌더 중에는 탭을 닫아도 계속 진행된다는 안내를 표시한다.

### 31.16 사용자 UI에 보여줄 방식

일반 사용자에게는 WASM·WebGPU·WebCodecs라는 용어를 전면에 내세우지 않는다.

다음 두 방식으로 표현한다.

- `내 PC에서 빠르게 만들기`
- `서버에서 안정적으로 만들기`

로컬 방식 상태 예:

- 내 PC 성능을 확인하고 있습니다
- 영상 제작 도구를 준비하고 있습니다
- 이미지와 음성을 정리하고 있습니다
- 장면을 만들고 있습니다
- 영상을 압축하고 있습니다
- 서버에 안전하게 저장하고 있습니다

폴백 안내 예:

`현재 PC에서는 영상 제작이 오래 걸리고 있어 서버 방식으로 이어서 만들고 있습니다. 이미 만든 원고·음성·자막은 그대로 사용합니다.`

사용자에게 실패처럼 보이지 않게 하지만, 실제 전환 사실은 숨기지 않는다.

### 31.17 관리자 진단 화면

관리자 화면에는 다음 정보를 제공한다.

- 브라우저 종류·버전

- WebCodecs 코덱 지원 결과

- Warm-up 시간
- 프레임 생성 시간
- 인코딩 시간
- Muxing 시간
- 업로드 시간
- 총 소요시간
- 평균 FPS
- 최대 정체 시간
- 폴백 여부와 원인
- 서버 렌더 소요시간
- 최종 검증 결과

개인정보나 과도한 장치 지문은 저장하지 않는다.

장치 정보는 문제 진단에 필요한 최소 수준으로 제한한다.

### 31.18 성능 계측 항목

Dell Beta에서 사용했던 세부 계측 방식을 확장한다.

TTS 계측:

- MP3 인코딩 시간
- 전체 TTS 시간

MP4 계측:

- 미디어 다운로드 시간
- 이미지 디코딩 시간
- 동영상 정규화 시간
- Worker 준비 시간
- WebGPU 준비 시간
- 프레임 생성 시간
- 평균·최저 렌더 FPS

이 데이터는 사용자의 화면에 모두 노출하지 않고, 관리자 성능 분석과 자동 권장 방식 결정에 사용한다.

### 31.19 자동 선택 정책

StoryMaker_C는 장기적으로 다음과 같은 자동 선택 정책을 가진다.

#### 로컬 우선

- WebGPU 실제 준비 성공
- WebCodecs 시험 인코딩 성공
- 입력 미디어 규모가 적정
- 직전 로컬 성공 이력 존재
- 예상 시간이 서버보다 짧음

#### 서버 우선

- 저사양 장치 추정
- 브라우저 미지원
- 메모리 위험
- 긴 영상·대량 미디어
- 직전 로컬 실패
- 모바일 환경
- 사용자가 탭을 닫을 가능성이 높은 작업

#### 사용자 선택 존중

자동 추천은 하되 사용자가 다른 방식을 선택할 수 있게 한다.

단, 명백한 미지원 환경에서는 불가능한 선택을 제공하지 않는다.

### 31.20 실전 성공 기준

단계 9의 성공은 개발자 PC에서 한 번 MP4가 만들어지는 것이 아니다.

다음 시나리오를 모두 통과해야 한다.

1. 고성능 PC 로컬 렌더 성공
2. 일반 노트북 로컬 렌더 성공
3. WebGPU 비활성 상태에서 WASM 또는 서버 전환 성공
4. WebCodecs 미지원 상태에서 서버 전환 성공
5. 저사양 PC에서 제한 시간 후 서버 폴백 성공
6. 로컬 렌더 중 취소 후 재시도 성공
7. 로컬 렌더 중 새로고침 후 상태 복구
8. 서버 렌더 중 탭 종료 후 보관함 완료 확인
9. 동일 작업 중복 렌더 방지
10. 기존 TTS·SRT 재사용 확인
11. 정확한 음악·TTS·자막 싱크 확인
12. 최종 MP4 DB·manifest·파일 해시 일치
13. 보관함 재생·다운로드 성공
14. 모바일에서 서버 방식 완주
15. 관리자 화면에서 폴백 원인 확인

### 31.21 회귀 금지 사항

다음 문제를 다시 만들지 않는다.

- 브라우저와 서버가 동시에 MP4 생성
- React 또는 여러 브리지에서 TTS 중복 실행
- DOM 감시와 직접 업로드가 동시에 실행
- 로컬 MP4 업로드 후 서버가 다시 렌더
- 정확한 SRT를 서버가 덮어씀
- 배경음악 혼합 파일을 무시함
- 작업 ID가 다른 결과에 연결됨
- 완료 이벤트가 여러 번 전송됨
- Worker가 종료되지 않고 다음 작업에 남음
- 전체 Raw Frame을 메모리에 적재
- `navigator.gpu` 존재만으로 WebGPU 성공 판정
- 코덱 지원 API만 믿고 실제 시험 인코딩 생략
- 120초 초과 후 사용자에게 아무 안내 없이 정지
- 폴백 시 원고·TTS부터 전부 다시 생성
- 최종 파일 검증 없이 보관함 완료 처리

### 31.22 단계 9 이후 Claude Code 적용 지시

Claude Code는 현재 단계 9에서 이미 만든 구현을 먼저 보존한다.

이 장을 읽은 뒤 다음 세 목록을 작성한다.

1. 이미 구현돼 검증된 항목
2. 구현됐지만 실전 검증이 부족한 항목
3. 빠져 있어 보강해야 할 항목

그다음 최소 보강 순서를 따른다.

1. 실제 기능 탐지와 시험 인코딩
2. Worker 및 렌더 잠금
3. 메모리 해제
4. 진행률 계약
5. 제한 시간과 정체 감지
6. 서버 폴백
7. 기존 산출물 재사용
8. 결과 계약 통일
9. 최종 MP4 검증
10. 사용자·관리자 UI 반영
11. 저사양 PC와 미지원 브라우저 E2E

현재 정상 동작하는 단계 8 FFmpeg 서버 렌더를 삭제하거나 약화하지 않는다.

로컬 가속은 서버 렌더를 대체하는 단일 경로가 아니라, 서버 비용을 줄이고 사용자 체감 속도를 높이는 추가 경로다.

서버 렌더는 최후의 임시방편이 아니라 공식적인 안정 경로로 유지한다.

최종 구조는 다음과 같아야 한다.

`기능 탐지 → 로컬 렌더 가능성 평가 → 로컬 렌더 → 성공 검증 → 서버 저장`

실패 시:

`로컬 상태 정리 → 기존 산출물 재사용 → 서버 MP4 렌더 → 성공 검증 → 동일 보관함 저장`

이 구조가 완성돼야 StoryMaker_C는 다양한 사용자 PC 환경을 감당하는 실제 서비스가 된다.
