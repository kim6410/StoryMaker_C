# StoryMaker Claude Lab - 단계 2 업무일지

작성일시: 2026-07-28

작업 목적: 독립 SQLite DB 기반 구축(중앙 연결 모듈, 스키마, 마이그레이션, CRUD, 무결성·동시성 검증)

사용자 요청: 1단계 화면 구조 승인 + 2단계 범위 12개 항목 지정(중앙 설정 모듈, SQLite 중앙 연결 모듈, WAL/foreign_keys/busy_timeout 공통 적용, 읽기전용 연결, commit/rollback/context manager, 스키마 버전·마이그레이션, 5개 핵심 테이블군, 상태값·오류코드 상수화, 바이너리 미저장, 상대경로 저장, CRUD 테스트, 무결성·동시접근 테스트). WordPress·AI·Supertonic·SRT·MP4·썸네일·실사용자 업로드는 이번 단계에서 연결하지 않음.

조사한 환경: 1단계에서 이미 조사 완료(Windows 11, Python 3.14.4, Node v24.17.0, FFmpeg 8.1, Git). 이번 단계는 추가 환경 조사 없이 기존 결과를 재사용함.

생성한 파일:
- app/config.py (프로젝트 루트·경로 중앙 계산, 상대경로 변환 유틸)
- app/constants.py (사용자 role/status, 프로젝트 상태 7종, 오류 코드 6종, 미디어 종류 5종 중앙 상수화)
- app/db/connection.py (중앙 SQLite 연결 모듈: get_connection/get_readonly_connection, WAL/synchronous=NORMAL/foreign_keys=ON/busy_timeout=5000, commit/rollback/close 자동화)
- app/db/migrations.py (schema_migrations 테이블 + 버전별 마이그레이션 실행기)
- app/db/repository.py (users/subscription_plans/user_subscriptions/projects/archive_items/audit_logs CRUD)
- scripts/db_selftest.py (마이그레이션 실행, CRUD, 무결성, 20스레드 동시쓰기 테스트, 반복 실행 가능하도록 자체 정리 포함)

수정한 파일:
- app/main.py: 기동 시 `run_migrations()` 자동 호출 추가, `/healthz`에 DB 무결성·journal_mode 포함

변경하지 않은 기존 영역: app/templates/*.html, app/static/*, run.bat, requirements.txt (1단계 산출물 그대로 유지, 화면은 아직 실제 DB와 연결하지 않음 — 이번 단계 범위 밖)

구현 내용 요약: 사용자 요청 12개 항목을 모두 반영한 독립 SQLite 계층을 처음부터 설계했다. 기존 StoryMaker V1/Beta의 DB 코드는 열람하지 않았으며, 이번 대화에서 별도로 정리된 "SQLite 모범 사례"(중앙 연결 모듈, mode=ro 읽기전용, PRAGMA 공통 적용, 상태 코드 중앙화, 오래된 DB 사본 방지용 상대경로 저장)를 요구사항 수준에서만 참고해 새로 구현했다.

테스트 결과: `scripts/db_selftest.py` 실행 결과 24/24 PASS (마이그레이션 1건, CRUD 19건, 무결성 3건, 동시성 2건). 상세는 본문 하단 참고.

PC 화면 확인 결과: `/healthz`가 `{"ok":true,"stage":"2-db","db_integrity":"ok","db_journal_mode":"wal"}`로 정상 응답. 1단계 화면 15개는 재기동 후에도 전부 정상 로딩(별도 재확인 완료).

모바일 화면 확인 결과: 이번 단계에서 화면 변경 없음(1단계 결과 유지, 별도 확인 불필요).

오류와 해결 내용:
- `scripts/db_selftest.py`를 두 번째로 실행했을 때 `subscription_plans.code` UNIQUE 제약 위반으로 실패함. 원인은 스크립트가 이전 실행의 샘플 플랜 데이터를 정리하지 않고 재실행됐기 때문. `_reset_previous_selftest_data()`를 추가해 매 실행 시작 시 자체 생성한 테스트 데이터만 선택적으로 정리하도록 수정 후 재실행하여 24/24 PASS로 해결. 실패 시점에도 `PRAGMA integrity_check`는 `ok`를 유지해, get_connection()의 예외 시 rollback 로직이 정상 동작함을 함께 확인함.
