# 2026-07-29 단계11 보완 - 콘텐츠 제작~결과 전체 흐름 단일 스크롤 페이지 통합

## 요청 배경

"3페이지 이상으로 제작해야 하는 새 콘텐츠제작 페이지를 전체 흐름에 따라가기 쉽게
한페이지로 해서 자연스럽게 상단으로 부터 하단으로 이동하면서 사용자가 작업을 진행하도록
만들어주면 됨." 이어서 "최대한 이전 사용자들이 낯설지 않게 V1의 Beta의 UI, UX를
벤치마킹해서 유사하게 만들어줘, 중요한건 지금 F:\StoryMaker_C 여기 준비된 엔진과 튼튼한
기반이 가장 중요하다"는 확인을 받음 — 즉 화면 흐름은 Dell Beta처럼 한 페이지로 자연스럽게,
그러나 이미 검증된 StoryMaker_C 자체 엔진(MP4 로컬/서버 폴백, TTS, 썸네일 등)은 절대
건드리지 않는 방향으로 진행.

## 문제였던 기존 구조

`/content/new`(입력) 제출 후 결과를 보려면 서로 다른 URL 5개를 옮겨 다녀야 했다.

`/content/job/{uid}`(상태) → `/channels`(SNS 8채널) → `/tts`(음성·자막) → `/mp4`(영상)
→ `/thumbnail`(대표 썸네일)

각 페이지 하단에 "다음: ..." 링크로만 연결돼 있어 전체 흐름을 한눈에 보기 어려웠다.

## 결정 사항과 이유

각 단계의 실제 처리 로직(라우트 함수, 서비스 계층, DB 스키마)은 **전혀 수정하지 않고**,
5개의 GET 페이지 템플릿만 하나로 합쳤다. 이유: 기존 정상 기능 보존이 최우선이고
(MP4 로컬/서버 폴백, TTS 문장별 재생성, 썸네일 8종 후보 등은 이미 실사용 검증된 복잡한
기능이라 로직까지 다시 쓰면 회귀 위험이 크다), 최소 수정으로 "한 페이지, 위→아래 진행"
요구를 만족시킬 수 있는 방법이었다.

## 구현

### 백엔드 (`app/main.py`)
- `GET /content/job/{job_uid}`(허브)가 이제 예전 5개 라우트가 각각 조회하던 데이터를
  전부 모아서 한 번에 반환한다: 상태·스냅샷, SNS 8채널, TTS 문장·마스터·SRT, MP4·장면·
  배경음악믹스, 썸네일 후보·대표 썸네일.
- `GET /content/job/{job_uid}/channels`, `/tts`, `/mp4`, `/thumbnail` 4개는 각각의
  로직을 전부 지우고 허브 URL(`#section-xxx` 앵커 포함)로 리다이렉트하는 한 줄짜리
  함수로 바뀌었다 — 기존 북마크·외부 링크가 깨지지 않도록 하기 위함(대시보드/보관함
  일부 템플릿이 여전히 이 URL들을 참조하지만, 리다이렉트 한 번으로 정상 동작한다).
- 채널 재생성/수정/되돌리기, TTS 생성/문장별 재생성, MP4 생성, 썸네일 후보생성/선택
  POST 액션들은 처리 로직은 그대로 두고 **성공/실패 리다이렉트 대상만** 허브 URL의
  해당 섹션 앵커(`#section-channels`, `#section-tts`, `#section-mp4`,
  `#section-thumbnail`)로 바꿨다.
- `/content/new`(딸깍 제작) 제출 성공 시 리다이렉트도 `/channels` 대신 허브
  `#section-channels`로 바뀌었다.
- 썸네일 저장 성공 플래그의 쿼리 파라미터명을 `saved` → `thumb_saved`로 통일했다
  (허브에 다른 섹션들의 오류 파라미터와 이름이 겹치지 않도록).

### 프론트엔드
- `app/templates/content_job_status.html` 하나에 5개 섹션(`#section-info`,
  `#section-channels`, `#section-tts`, `#section-mp4`, `#section-thumbnail`)을
  위→아래로 배치. 각 섹션은 기존 개별 페이지의 마크업·JS를 그대로 가져왔다(탭 전환,
  글자수 카운터, 복사 버튼, 로컬 렌더 진행률, 썸네일 후보 선택 모달 등 전부 동일).
- 이전 단계가 끝나지 않았으면(TTS는 영상원고, MP4는 TTS 완료, 썸네일은 MP4 완료 필요)
  해당 섹션에 "먼저 위 N단계에서 ...를 완료해 주세요" 안내만 보여주고 실제 폼은
  숨긴다 — Beta의 "딸깍" 한 페이지 진행 흐름과 동일한 느낌, 아래로 스크롤하며 순서대로
  완료하면 된다.
- `app/templates/_step_indicator.html`의 단계 링크를 별도 URL 대신 같은 페이지 안의
  앵커(`#section-*`)로 바꿔, 상단 진행 표시를 클릭하면 페이지 이동 없이 스크롤만 된다.
  ('완료·보관함' 단계만 실제로 다른 화면(보관함 상세)이라 그대로 외부 링크 유지.)
- 이제 쓰이지 않게 된 `content_job_channels.html`, `content_job_tts.html`,
  `content_job_mp4.html`, `content_thumbnail.html` 4개 템플릿 파일 삭제(참조 검색으로
  다른 곳에서 쓰지 않는 것 확인 후 삭제).

## 검증 (포트 8033, 8032/8031 무관섭)

httpx E2E로 처음부터 끝까지 실제로 돌려봄(Gemini는 실제 호출, TTS·MP4·썸네일은 로컬
Supertonic/FFmpeg라 추가 과금 없음):

1. 딸깍 제작 제출 → 허브 URL로 리다이렉트(더 이상 `/channels` 별도 경로 아님) 확인
2. 허브 페이지 하나에 5개 섹션 id가 모두 존재하는지 확인
3. 예전 개별 URL(`/channels`, `/tts`, `/mp4`, `/thumbnail`) 각각 GET 요청 시 허브
   URL의 올바른 `#section-*` 앵커로 303 리다이렉트되는지 확인(하위 호환)
4. 채널만 완료된 상태에서 TTS 섹션은 실제 폼이 보이고, MP4·썸네일 섹션은 여전히
   "먼저 완료해 주세요" 안내만 보이는 단계 게이팅 확인
5. TTS 생성 → MP4 섹션 잠금 해제 확인 → MP4 생성(서버 방식) → 썸네일 섹션 잠금 해제
   확인 → 썸네일 후보 생성 → 후보 선택·저장까지, 전체 파이프라인이 이 한 페이지
   안에서 끝까지 정상 동작함을 확인 — 전부 PASS.
6. `scripts/db_selftest.py` 24/24 PASS(회귀 없음).

테스트 스크립트는 검증 후 삭제, 8033은 종료함. 8032는 이번에도 건드리지 않음 —
반영하려면 사용자가 8032를 재시작해야 한다(uvicorn 코드 자동 반영 안 됨).

  남으므로 문제 없음.
