## 1. 작업 배경

단계10A·단계10에서 반복적으로 이연됐던 마지막 항목인 "썸네일 8종 선택 기능"을
완성한다. 착수 전 현황조사는
`2026-07-29_단계10_썸네일8종선택_현황조사_구현계획.md`에 기록했다. 요약:
- 기존 `/content/thumbnail`은 완전한 mock 화면(숫자만 표시, 저장 버튼이 실제로는
  `/archive`로 이동하는 링크)이었다.
- `archive_items` 테이블이 `media_type='thumbnail'`, `is_primary`,
  `media_deleted_at` 컬럼을 이미 갖추고 있었지만 한 번도 쓰이지 않아 그대로
  재사용했다(새 마이그레이션 없음).
- 이미지 생성은 완성된 MP4에서 FFmpeg로 서로 다른 8개 시점의 프레임을 추출하는
  방식을 선택했다(신규 외부 서비스·API 키 없음).

| URL | 기능 |

## 4. 저장 규칙과 동시성 안전성

- 후보 8장은 `data/jobs/{uid}/media/thumbnails/cand_0.jpg`~`cand_7.jpg`(저장
  개수 제한과 무관한 미리보기 풀). 대표 썸네일은 `archive_items`에
  `media_type='thumbnail'` 행이 **활성 상태로 최대 1개**만 존재하도록
  `save_primary_thumbnail()`이 보장한다: 기존 활성 행을 소프트 삭제하고 새 행을
  삽입하는 것을 하나의 `get_connection()` 트랜잭션 안에서 처리하며,
  `app/db/connection.py`의 전역 `_WRITE_LOCK`이 프로세스 내 모든 쓰기를
  직렬화하므로 동시 요청·이중 클릭에도 항상 활성 행 1개로 수렴한다.
- 재선택 시 새 파일(`selected_{랜덤}.jpg`)을 만들고 옛 파일은 실제로 삭제해
  "파일과 DB 참조가 함께 교체"되도록 했다.

## 6. 테스트 도구 한계로 대체 검증한 항목

이번 세션의 claude-in-chrome 자동화 도구에서 두 가지 한계를 발견해 대체 검증
방법을 썼다(앱 코드의 결함이 아님, 도구 쪽 문제로 판단한 근거를 함께 기록한다).

1. **키보드 이벤트 미전달**: `computer` 도구의 `key` 액션(Enter, Space, 알파벳
   키 전부)이 포커스된 요소는 물론 `document`에 캡처 단계로 등록한 리스너에도
   전혀 도달하지 않았다(빈 문자를 눌러도 `keydown` 이벤트 자체가 관측되지 않음).
   실제 키 입력을 시뮬레이션하는 `KeyboardEvent`를 코드로 직접 `dispatchEvent`한
   결과 Enter·Space 모두 정확히 후보를 선택했고 ESC도 정확히 모달을 닫았다 -
   이벤트 핸들러 자체는 정상이며, 이 세션에서 도구가 실제 OS 키 입력을 이
   탭에 전달하지 못하는 문제로 판단했다.
2. **POST fetch 간섭**: 관리자 검증 때는 `fetch(..., {method:'POST'})`가
   정상 동작했지만, 이번에는 동일한 패턴의 POST 요청이 한 번은
   `[BLOCKED: Cookie/query string data]`로 명시적으로 차단됐고, 다른 한
   번은 현재 페이지(`/content/new`)의 완전히 다른 폼 필드(`topic`) 검증
   오류를 반환했다(요청 대상 URL과 무관한 오류) - 요청이 실제로 내 라우트에
   도달하지 못하고 도구가 가로챈 것으로 판단했다. 대신 GET 기반 접근 차단은
   fetch로 안정적으로 확인했고(404 응답), POST 라우트의 소유권 검사가
   함수 최상단(폼 파라미터 바인딩 다음, 비즈니스 로직 이전)에 있음을 소스
   코드로 직접 재확인해 접근 제어가 GET 라우트와 동일한 방식으로 보장됨을
   교차 검증했다.
