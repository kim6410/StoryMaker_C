# 썸네일 8종 선택 기능 - 현황조사 및 구현계획

작성일: 2026-07-29
기준 커밋(작업 시작 시점): 6c5a595 (origin/main과 일치 확인)

## 1. 착수 전 현황조사

- `/content/thumbnail` URL이 이미 존재했지만 `content_thumbnail.html`은 완전한 mock
  화면이었다: `candidates=list(range(1,9))`로 숫자만 넘기고, 화면에는 "템플릿 N"
  텍스트만 표시, 3번이 하드코딩으로 미리 선택된 것처럼 보이며, "저장" 버튼은 실제 POST
  없이 `<a href="/archive">`로 이동만 한다. 완료 기준(mock 전용 화면 금지)을 위반한다.
- `projects.status` 상태머신(`app/content/steps.py`의 `STEP_DEFS`/`_STATUS_STEP_INDEX`)에는
  썸네일 단계가 없다. 여기에 새 단계를 추가하면 이미 검증된 6단계 인디케이터와 대시보드
  집계 로직을 모두 건드리게 되어 회귀 위험이 커진다. **자동 선택: 상태머신은 건드리지
  않고, MP4 완성 이후 별도 진입점으로 썸네일 선택 화면을 연결한다**(기존 정상 기능 보존
  우선순위 1번).
- `archive_items` 테이블은 이미 `media_type CHECK (... 'thumbnail' ...)`,
  `is_primary`, `media_deleted_at` 컬럼을 갖추고 있었지만(2단계 마이그레이션) 실제로는
  단 한 번도 쓰이지 않았다(0행). **자동 선택: 새 테이블을 만들지 않고 이 테이블을
  그대로 재사용한다**(최소 수정, 기존 데이터 계약 보존).
- FFmpeg는 `app/media/renderer.py`에 `_run_ffmpeg()` 헬퍼로 이미 프로젝트 전용 실행
  경로(`runtime/ffmpeg`)를 통해 안정적으로 쓰이고 있다(단계8·9에서 검증 완료).

## 2. 이미지 생성 방식 결정

지시서가 제시한 선택지(기존 사진·영상 프레임·브라우저 Canvas·프로젝트 내부 독립 처리)
중 **완성된 MP4에서 FFmpeg로 서로 다른 8개 시점의 프레임을 추출**하는 방식을 선택했다.

이유:
1. 이미 검증된 FFmpeg 실행 경로만 재사용 - 신규 외부 서비스·API 키·모델 다운로드 없음.
2. 완성된 영상 자체가 각 프로젝트마다 실제로 다른 장면·문구·색상을 담고 있으므로(단계8
   장면 계획), 8개 시점을 고르면 진짜로 서로 다른 8장이 나온다(가짜 배리에이션 없음).
3. 브라우저 Canvas 캡처 방식은 클라이언트 쪽에서 `<video>` 프레임을 캔버스로 그린 뒤
   업로드하는 별도 JS 파이프라인이 필요해 구현·검증 범위가 커지고, seek 이벤트 타이밍에
   따라 브라우저마다 프레임 캡처 시점이 달라질 수 있어 "서버에는 선택 전 0개" 요구사항을
   깨끗하게 만족시키기 더 어렵다고 판단했다.
4. MP4가 없으면애초에 원본 프레임이 없으므로, 이 방식은 자연스럽게 "MP4 완성 후에만
   썸네일 선택 가능"이라는 흐름을 강제한다(단계10 지시서의 제작 순서와 일치).

시점 선택: 페이드인·아웃 구간을 피해 영상 길이의 5%~92% 구간을 8등분한다.

## 3. 저장 규칙 설계

- 후보 8장: `data/jobs/{job_uid}/media/thumbnails/cand_0.jpg`~`cand_7.jpg`. 이미 8장이
  모두 있으면 재생성하지 않는다(불필요한 재작업 방지, 지시서 15번 원칙과 동일 정신).
  이 파일들은 "저장된 대표 썸네일"이 아니라 미리보기 후보이므로 DB에 기록하지 않는다.
- 대표 썸네일 1장: `archive_items` 테이블에 `media_type='thumbnail'`,
  `is_primary=1`인 행이 최대 1개만 존재하도록 관리한다. 선택 시 기존 활성 행을
  같은 트랜잭션 안에서 소프트 삭제(`media_deleted_at`)하고 새 행 1개를 삽입한 뒤, 그
  트랜잭션이 끝난 뒤 옛 파일을 실제로 지운다. `app/db/connection.py`의 전역
  `_WRITE_LOCK`이 프로세스 내 모든 쓰기 연결을 직렬화하므로, 이 삭제+삽입을 한 트랜잭션
  안에 넣으면 이중 클릭·동시 요청이 와도 항상 활성 행이 정확히 1개로 수렴한다.
- 재선택 시 새 파일 이름(`selected_{랜덤10자}.jpg`)을 매번 새로 만들어 옛 파일과
  물리적으로 구분되게 한다(교체가 실제로 파일 단위에서 일어났음을 명확히 확인 가능).

## 4. 접근 제어

- 페이지·후보이미지·선택저장·대표이미지 라우트 모두 기존 `_get_owned_project_or_none()`을
  재사용한다(본인 소유이거나 관리자만 통과, 단계5부터 검증된 패턴).
- 후보 생성은 GET에서 자동 실행하지 않고 명시적 POST 버튼(기존 AI/TTS/MP4 생성과 동일한
  UX 패턴)으로 트리거한다.

## 5. E2E 검증 계획

8033 임시 서버에서 완성된 MP4가 있는 프로젝트로 다음을 확인한다: 후보 8장 실제로 서로
다른 이미지인지 육안 확인, 선택 전 `archive_items`에 thumbnail 행 0개(SQL 직접 확인),
선택 후 정확히 1개, 재선택 후에도 1개(파일도 교체됨), 새로고침·로그아웃/재로그인 후
유지, 보관함 목록·상세에 대표이미지 반영, 다운로드 동작, 타 사용자 계정으로 후보·선택
URL 직접 접근 차단, 모바일 레이아웃, 키보드 Enter/Space/ESC.
