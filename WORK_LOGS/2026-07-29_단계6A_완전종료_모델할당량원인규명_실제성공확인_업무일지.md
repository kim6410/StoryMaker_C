**결론: 두 프로젝트는 완전히 동일한 키를 쓰고 있었다. 429의 원인은 키·결제 문제가 아니라 "요청한 모델"이었다.** 같은 Google Cloud 프로젝트 안에서도 모델별로 무료 등급 할당량이 다르게 배정되어 있었고, `gemini-2.0-flash`는 할당량 0, `gemini-3.5-flash-lite`는 정상 배정 상태였다.

키 원문은 이 문서를 포함한 어떤 산출물에도 출력하지 않았다(해시 앞 12자리만 비교에 사용).

## 4. 실제 검증(단일 호출, 반복 호출 아님)

임시 진단 스크립트(`scratchpad/probe_gemini_model.py`, 프로젝트 밖 세션 스크래치패드, 저장소에 포함되지 않음)로 두 모델에 각 1회씩만 직접 호출했다.

| 모델 | 결과 |
|---|---|
| `gemini-3.5-flash-lite` | HTTP 200, candidates=1, has_text=True |
| `gemini-2.0-flash` | HTTP 429 (동일 키, 동일 순간) — 모델별 할당량 차이를 다시 한번 실증 |

## 5. 적용한 수정

`F:\StoryMaker_C\config\.env`의 `GEMINI_MODEL` 값을 빈 문자열에서 `gemini-3.5-flash-lite`로 설정했다.

- 코드(`app/config.py`, `app/integrations/gemini_client.py`)는 전혀 수정하지 않았다.
- `config/.env`는 Git에 포함되지 않는 파일이라 이 변경은 커밋 대상이 아니다(`.gitignore` 확인 완료).
- Beta의 환경변수(`BETA_GEMINI_MODEL` 등)를 StoryMaker_C가 직접 참조하도록 만들지 않았다. StoryMaker_C는 자기 자신의 `GEMINI_MODEL` 설정만 사용하는 완전 독립 구조를 유지했다.

## 6. 실제 서버 재기동 관련 제약

기존에 실행 중이던 서버 프로세스(PID 7736, port 8031 LISTEN 확인)를 재기동해 설정을 반영하려 했으나, 같은 사용자 계정임에도 `Stop-Process`가 `Access is denied`로 실패했다(정상 권한/샌드박스 해제 모두 시도). 이는 해당 프로세스가 더 높은 무결성 수준으로 시작되었을 가능성이 높으며, 이 세션에서는 강제 종료 권한이 없다.

기존 서버를 중복 실행하지 않는다는 원칙(작업지시 6장)에 따라 port 8031에 새 서버를 띄우지 않았다. 대신 FastAPI 앱을 같은 코드베이스에서 새 파이썬 프로세스로 불러와(`httpx.ASGITransport`, 포트를 점유하지 않는 인프로세스 방식) 실제 회원가입 → 이메일 인증 → 로그인 → 업체정보 저장 → 콘텐츠 작업 생성 → Gemini 생성 요청까지 전 구간을 실제 코드 경로로 검증했다. 새 파이썬 프로세스이므로 `config/.env`의 새 `GEMINI_MODEL` 값이 정상적으로 로딩되었다.

**남은 사항**: 브라우저로 접속하는 실제 개발 서버(포트 8031, PID 7736)는 사용자가 직접(또는 상위 권한 세션에서) 재시작해야 이 설정이 반영된다. 코드는 수정하지 않았으므로 재시작만으로 충분하다.
