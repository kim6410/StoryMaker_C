## 3. 사용자 플로우 변경 요약

기존에는 대시보드/보관함이 정적 샘플이라 "가입→로그인 이후 실제로 뭘 볼 수 있는지"를

결과 확인→보관함 목록/상세→다운로드→삭제→로그아웃→재로그인 후 상태 유지 확인.

## 7. 이번 회차에 발견하고 수정한 실제 버그 1건

**증상**: 보관함 상세에서 "영구 삭제"를 실행하면 DB 행은 정상 삭제되지만(FK CASCADE 정상),
`data/jobs/{job_uid}` 폴더 내 `media/final.mp4` 파일이 즉시 지워지지 않고 남는 경우가 있었다
(`shutil.rmtree(..., ignore_errors=True)`가 Windows 파일 잠금 실패를 조용히 무시).
직접 재현: 삭제 직후 별도 스크립트로 같은 폴더를 다시 지워도 실패했고, 8032 테스트 서버
프로세스를 완전히 종료한 뒤에야 삭제에 성공했다 — 즉 원인은 브라우저가 아니라 방금까지
해당 파일을 스트리밍하던 서버 프로세스 쪽의 일시적 파일 핸들/커넥션이었다.

**수정**: `app/main.py`의 `archive_delete()`에 최대 5회(0.5초 간격) 재시도를 추가했다
(`app/main.py:864` 부근). 일반적인 사용 시나리오(파일을 보다가 몇 초 뒤 삭제)에서는 이
재시도로 충분히 해결될 것으로 판단하지만, 삭제 직후 즉시(수백 ms 이내) 재삭제를 시도하는
극단적 경우 재시도 창을 넘길 가능성은 이론적으로 남아있다. DB 행은 이미 삭제되어 사용자
화면·API에는 절대 노출되지 않으므로 기능·보안상 영향은 없고, 디스크 정리 지연 가능성만
남는 낮은 리스크로 판단해 별도의 백그라운드 정리 작업 등 추가 구조는 만들지 않았다
(최소 수정 원칙).
